# Agent 对话输入存储

本文明确保存“用户原始输入”和“注入上下文后的 Runtime 输入”两种记录，用于展示和故障排查。主页及未来的 Workflow 上下文对话统一采用此方案。

状态：双份输入的存储代码已部署；真实成功对话已核对原始消息加密、私有 Runtime 输入加密、版本上下文及资源附件快照；Workflow 上下文绑定、输入注入和画布对话入口已部署，并完成多节点、多上下文实机验证；完整异常与生命周期验收尚未完成。

## 两类记录

- `chat_messages` 保存用户原始文本（包括 `/workflow` 等 command），供前端展示。原始附件引用和消息时间沿用现有存储。
- `agent_runs` 的加密私有 `input_snapshot` 保存同一轮的原始 `content`，以及面向 Runtime 的上下文和输入。通过 `chat_id`、`run_id`、`input_message_id` 关联展示消息。

新增私有字段：

| 字段 | 含义 |
| --- | --- |
| `runtime_message` | 去除 command 前缀后交给 Runtime 的消息 |
| `resolved_runtime_instructions` | 本轮解析的完整指令，包括正文、名称、版本和激活标记；并非所有指令都会在已有会话中重复发送 |
| `runtime_inputs` | Runtime 各次提交边界的输入快照列表，包括普通发送、空回复重试、command 完成提醒及宿主自动续接 |

每份输入快照记录事件 ID、数据库记录时间、提交原因、续接索引、原生 thread ID、客户端消息 ID、完整 input 数组、模型、推理强度和是否恢复历史。`input` 是最终拼装结果，包含本次真正追加的背景说明、历史恢复提示及附件文本/图片路径等；附件二进制继续由原有文件存储管理。

## 边界与权限

快照在 `turn/start` 调用前产生，状态为 `prepared_for_submission`：说明输入已经准备好，不表示模型已经接收或执行成功。执行成功/失败仍由执行记录和运行事件判断。它是提交给 Runtime 的输入，不是底层模型供应商请求的完整归档；原生会话中的历史、自动压缩及后续工具结果不在这份输入数组里。

`runtime.input` 是内部事件：宿主按租户、用户、Chat 和执行绑定保存到已有加密字段，不投影为聊天气泡或 SSE，不进入公开执行事件；常规诊断只返回原有元信息。按事件 ID 去重，同一轮的多次提交分别保留。保存不需要新增表或数据库迁移。

新数据从功能启用后的执行开始积累，不为历史执行伪造背景快照。连接密钥、环境变量和认证配置不作为快照字段复制。

## 验证

验证原始文本与展开内容同时存在、加密后可重新读取、多次提交不覆盖、重复事件不重复保存、错误 Chat 绑定被拒绝，以及展开内容不会进入前端事件或常规诊断。Runtime 测试应对比快照 input 与实际 `turn/start` input，并覆盖 command 注入和内部重试。

## 排查用途与读取方式

从 `chat_id` 和消息 `message_id` 定位 `input_message_id` 对应的执行 `run_id`，读取原始消息、执行私有快照，再按该执行联查工具事件、错误和最终状态。用于回答：

- 用户原始请求是什么，command 是否被正确识别、剥离和展开？
- 当时注入了哪个版本的指令，哪些说明在该次输入中真正发送，哪些由已有原生会话承接？
- 附件引用、可读路径和内容快照是否正确，是否经历原生历史恢复？
- 同一轮为什么多次提交，每次内部重试或自动续接追加了什么提示？
- 对 Workflow 对话，当时关联哪个 Workflow、大版本、子版本、节点／连线及运行记录？

Workflow 特有的结构化关联字段已由画布对话上下文提供器写入该轮私有快照；不得用当前最新版 Workflow 或当前 prompt 模板重新生成旧执行输入，冒充当时的实际快照。具体实现进度与待验收项见 [Workflow 画布上下文对话设计](workflow-canvas-chat-design.zh-CN.md)。

双份记录不是两套互相复制的完整 transcript：原始用户消息和 Agent 回复沿用 Chat 消息存储，展开输入按执行追加保存；工具结果继续由执行事件记录。排查完整过程时将这些记录按 ID 和时间关联，而非只阅读展开输入。

失败、取消的执行也保留已经生成的记录；没有产生 Runtime 输入快照时应显示“未记录／尚未进入提交阶段”，不能据此认定模型已经接收消息。历史执行无快照时明确标为缺失。

当前不新增前端诊断入口或对外导出接口。后续如提供排查页面／工具，必须沿用 Chat 及关联资源的授权后读取解密内容，不能把私有输入批量放进普通列表、SSE 或服务日志。资源删除沿用既有删除策略，不新增短期自动清理规则。


## 2026-10-03 扩展核对

已在真实数据库中核对 29 条独立执行记录（含 3 条失败执行），覆盖多种节点、全局／节点／连线背景以及 v1／v2 大版本的原始消息和私有输入。原始消息与私有输入均有加密存储，已提交的 Runtime 输入包含服务端生成的 Workflow 上下文；公开执行事件中没有 `runtime.input`。Agent 提交新子版本后，旧执行仍记录当时的输入版本，不跟随当前 HEAD 改写。

模型启动前失败的样例保留原始消息和已解析上下文，但 Runtime 提交快照为空；模型容量错误及回复中断的样例则保留已生成的提交快照和失败状态。两者应明确区分，不能将空列表当作已提交输入，也不能将正常 SSE EOF 当作成功。

资源附件引用的实机核对同时检查了用户原始请求、服务端解析的固定版本节点／连线快照、私有 Runtime 输入和公开事件。历史会话在正常沙盒释放后仍能恢复，并读取先前持久化的结果文件；这项不等于已验证所有写回失败、取消与内部续接情形。

具体节点矩阵、发现的问题和未完成门槛继续以 [Workflow 画布上下文对话设计](workflow-canvas-chat-design.zh-CN.md) 为准；尚未满足整体交付条件。

共享生命周期补验后再次核对真实数据库：共 37 条独立执行，其中成功 33 条、失败 3 条、取消 1 条。全部原始消息和私有快照均加密保存，公开执行事件均没有 `runtime.input`。取消执行仍保留其已产生的一份 Runtime 提交快照，没有因取消而删除输入证据。该核对仍不替代内部空回复重试与自动续接的实机覆盖。

追加附件、刷新恢复及 Skill/MCP 验收后，真实数据库核对覆盖 46 条独立执行（42 条成功、3 条失败、1 条取消）。全部原始消息和私有快照加密保存，公开事件均无 `runtime.input`；其中 45 条有一份 Runtime 提交，1 条在提交前失败而没有提交快照。本轮没有多次内部提交样例，不将这些记录当作空回复重试或自动续接的证明。

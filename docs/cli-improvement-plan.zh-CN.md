## 第 3 项 异步执行后的完整结果获取

已新增 `flowork-cli deployment result --deployment_id ID --execution_id ID`，从持久化执行结果读取完整 EndNode 输出，适用于同步与异步调用。外部 API 和 Webhook 保持原有查询能力。

info、status、history、logs 分别负责资源配置、单次运行状态、历史列表和单次执行日志。result 是只读查询，不提交新执行、不等待执行完成；run 返回后会提示使用 result 回查。

返回约定：

- 执行中或等待审批：result_available=false、outputs=null、result_unavailable_reason=execution_pending。
- 成功且存在完整结果：result_available=true，outputs 为完整业务输出，包括合法的空对象 {}。
- 失败、超时或取消：保留终态和 execution_error，outputs=null，原因是 execution_unsuccessful。
- 成功但完整历史结果缺失：result_available=false、outputs=null，原因是 result_not_recorded；不以 result_summary 代替完整结果。
- 查询成功与业务执行成功分开：查询正常时 command_status=succeeded，调用方仍须检查 execution_status 和 result_available。

服务端校验当前用户的查看执行权限、调用所属 Deployment，以及持久化轨迹的来源。仅返回最终输出，不返回内部节点输出或完整工作流。CLI 帮助和 Agent 指引同步更新。

验证记录：96 项相关自动化检查通过；真实服务完成审批等待时查询、自动超时后以原执行 ID 回查完整嵌套输出、同步调用回查、失败结果回查，以及查询不新增执行的核对。验收资源已清理。

## 第 4 项 Skill 和 Workflow 版本冲突保护

实现约定：

- `skill publish`、`knowledge publish` 必须传 `--expected_version N`，使用下载返回的已发布版本。
- `workflow upload` 必须传 `--expected_version vN.svM`，检查目标大版本的最新小版本；其它大版本的更新不会制造冲突。
- 创建资源不需要预期版本。服务端在同一资源行锁事务内检查并保存，等待审批后仍使用原基准版本重新检查。
- 版本不同返回 HTTP 409 / CLI `version_conflict`，包含 expected_version、current_version 和处理提示；CLI 非零退出，不产生新版本。
- Skill、Knowledge 的整包发布遇到未发布草稿返回 `draft_conflict`，不替换草稿。需先检查并发布已有草稿，再重新下载并合并本地修改。Knowledge 旧文件上传、删除入口也受版本及草稿保护。
- 网页自动记录编辑基准，后台元信息刷新不会推进基准版本。冲突时保留本地内容和撤销历史。Skill 草稿保存和发布强制携带内容哈希，发布时在同一行锁下校验草稿基准。
- 不提供 force 参数，不自动用最新版本替换基准重试。CLI 帮助、Agent 提示词、前端 API 与 OpenAPI 契约同步调整。

兼容性：旧更新客户端不传基准版本时明确失败（API 422 / CLI 参数错误），不能继续无条件覆盖。CLI 工作流多步操作的整组保存语义见第 5 项。

验收记录（2026-10-03）：自动化验证并发只能单次成功、跨大版本独立性、草稿保护、审批期间版本变化、缺失参数和网页本地内容保留。真实服务中，Workflow 与 Skill 并发提交分别返回 200 和 409；Skill 草稿未被覆盖，处理草稿后正常发布；Knowledge 旧写入接口无法绕过版本及草稿保护。浏览器对过期基准保存返回 409，保留节点编辑，重新读取后保存返回 200，保留另一位编辑者的修改。真实 Terra Agent 仅收到业务目标，自行发现命令参数，完成三个 CLI 的缺失参数、旧副本拒绝、实际内容合并及成功发布验收；Agent 草稿场景由真实 API 测试补足。测试资源已清理，私有验收证据不入库。

## 第 5 项 Workflow 多步修改的原子保存

原始问题描述：workflow operation 连续执行多个修改时，如果中途失败，会将前面成功的修改保存为新版本。例如“添加节点成功 → 修改配置成功 → 连线失败”，最终仍保存前两步。Agent 容易将命令失败理解为没有修改，重试后造成重复操作。

实现约定：

- 读取并锁定目标 Workflow，在内存副本上按顺序执行全部操作；全部成功后通过现有版本仓库一次提交，内容和版本指针在同一事务内保存。
- 任一步失败，丢弃整组内存修改，不保存前半段、不新增版本；不经过临时文件和 upload，也不逐步写数据库再撤销。
- 失败返回原版本、applied=0、零起始 failed_index、failed_operation 和原因。前面已尝试的步骤标记 not_saved，失败步骤标记 failed，后续步骤计入 skipped。修正后重新提交整组，不提供部分保存开关。
- 全部成功只产生一个新版本，步骤状态为 saved。保存结果未知时仍返回 result_unknown，先查版本与内容，不能盲目重试。
- 成功提交后才发送画布更新通知；失败不触发已保存通知。接收该 Agent 事件的页面会重新拉取 Workflow；有未保存手动修改时保留草稿并提示选择。独立浏览器的跟随规则见下文。
- CLI 帮助、Agent 操作指引和指引版本号同步更新。

这里要求的是每个编辑操作本身成功，不要求编辑中的 Workflow 已经完整可执行。仍然允许保存尚未完成的草稿，不能将执行前的完整性校验强加到每次编辑保存。

画布独立跟随大版本：

- `/workflow/ID/version/vN` 表示持续跟随指定大版本的最新小版本。普通画布进入时确定当前大版本后转到该地址；打开一个恰为最新的小版本时也转为跟随。左侧大版本列表直接进入该地址。
- 已是历史小版本的地址保留固定快照；Task、Deployment、Trace 的只读快照入口保持原有固定版本语义。
- 可见页面每 3 秒查询受查看权限保护的 `/head?major=N`，只返回 major/sub 和 Workflow 更新时间标识 tree_revision；不反复下载完整 Workflow 或完整版本历史。隐藏标签页停止定时检查，返回时重新检查。版本未变化不加载画布，新内容加载期间保留旧画布。
- 某个大版本保存会移动全局 HEAD，但正在跟随其它大版本的画布不会随之跳转。有未保存草稿时提示选择，保留原编辑基准，不能自动覆盖。
- 前端保存始终指定目标大版本，使用实际加载的版本作为 expected_version。Agent operation/upload/layout 本来就强制传 --major，不依赖浏览器或对话的当前选择。


验收记录（2026-10-03）：后端原子保存回归 317 项通过，补充版本查询及运行时回归 95 项通过；前端画布、路由和通知相关检查通过，生产构建通过。真实 Terra Agent 仅收到业务目标，自主发现命令，验证末步失败与首步失败均不增版本、修正整组只产生一个新版本、不可执行草稿可保存；核对实际 CLI 输出和下载结果。真实服务中以独立浏览器上下文验证两个大版本各自刷新、全局 HEAD 变化不串版、历史快照固定、未保存编辑保留及加载新版操作；全局 HEAD 在 v2 时，v1 画布保存仍返回 v1 的新小版本（HTTP 200），浏览器无脚本错误。临时 Workflow 已删除，验收凭据和证据不入库。

版本目录补充（2026-10-03）：Explorer 使用两层结构，第一层为 major，点击跟随该大版本最新小版本；左侧独立按钮控制折叠，默认展开当前大版本，刷新保留用户折叠选择。第二层按 sub 倒序展示全部小版本，点击进入带 snapshot=1 的固定快照，即使当时是最新小版本也不会自动转为跟随。收到 Agent 的 VIBE_ACTION / META_SYNC / WORKFLOW_SYNC 通知时，同时使画布、head 和版本目录查询失效以立即更新；独立浏览器通过现有 head 检查中的 tree_revision 感知其它大版本新增和更新，重新获取目录，不切换正在查看的大版本。没有增加额外服务或长期连接。49 项前端检查、3 项接口检查及生产构建通过；真实浏览器验证两层展示、折叠不跳转、新增其它大版本可见、折叠状态保留、小版本增加、固定快照不跟随，以及点击大版本回到最新内容，浏览器无脚本错误，测试 Workflow 已删除。

## 第 6 项 次要易用性调整

### 评估配置

原始问题描述：task evaluation-config 必须传评估脚本，单独开关自动评估也需要重新提供脚本。

建议允许只修改 --auto-evaluate，未提供脚本时保留已有脚本。没有已有脚本时如何启用自动评估，以及空参数提交的行为，留待设计确认。

### 参数命名

原始问题描述：同类输入文件参数存在 --input-file、--input_file、--inputs_file，Agent 容易混用。

建议统一推荐写法，保留旧参数兼容，并同步调整帮助说明和示例。具体统一名称、适用命令及别名冲突处理待讨论。

### 列表筛选

原始问题描述：Skill、Knowledge、MCP 使用 --search，Task 使用 --query，Workflow 和 Deployment 的筛选能力较少。

建议统一名称、描述筛选参数及帮助说明。筛选范围是资源元信息；文件内容检索仍通过下载后的 bash 命令完成，不增加文件内容搜索命令。具体参数名称及兼容策略待讨论。

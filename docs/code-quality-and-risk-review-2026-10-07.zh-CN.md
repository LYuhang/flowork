## 1. Skill ZIP 解压前限制资源消耗

位置：[skill_bundle.py](../api/src/vibecanvas_api/services/skill_bundle.py) 的 `unpack_skill_zip`；[skills.py](../api/src/vibecanvas_api/routes/skills.py) 的 `_read_custom_bundle`。

当前逐项通过 `archive.read(info)` 将完整文件读入内存，再由 `validate_skill_files` 校验文件数量、单文件和整包大小。上传端也先完整读取压缩包。当前限制为最多 256 个文件、单文件 2 MiB、整包 16 MiB，但校验时机不能限制此前已经发生的读取和解压开销。

本地隔离验证将单文件限制临时设为 1,024 字节：一个 193 字节的 ZIP 在报错前已读取 65,536 字节。未在真实服务投递解压炸弹，也未验证绕过病毒扫描；生产已有 clamd 扫描不能代替应用自身的资源上限。

建议：

- 限制上传压缩包的实际读取字节数。
- 解压前检查条目数、声明的单文件大小和总大小。
- 解压时继续累计实际字节数并限制读取，不能仅信任 ZIP 元数据。
- 保留路径、链接和病毒检查，统一损坏及加密压缩包的错误输出。

验收：正常包可用；超数量、单文件、总量及高压缩比样例在超限前停止读取；错误明确；用受控样例验证内存和响应时间，不对生产做破坏性测试。

## 2. 修复对话历史中间区间缺失

位置：[history-window.ts](../web/src/pages/chat/history-window.ts)、[use-conversation-history.ts](../web/src/lib/chat/use-conversation-history.ts)、[ChatPage.tsx](../web/src/pages/chat/ChatPage.tsx)。

当前合并会去重并取较小 offset，但没有记录已加载区间是否连续；`hasOlder` 主要依据 `offset > 0`。旧缓存与新窗口不相接时，中间消息可能缺失且没有继续加载入口。

直接调用现有 TypeScript 合并函数的复现：缓存消息 1–30（total=30、offset=0），随后刷新得到 71–100（total=100、offset=70）。合并后只有 60 条，offset=0、hasOlder=false，消息 31–70 缺失。此前解决的短暂消失和空检查点问题不等于已覆盖此场景。

建议记录连续覆盖范围或使用明确的分页游标；发现区间缺口时补齐，不能将最小 offset 当作完整性证明。保留去重、时间顺序和视口锚点。

验收：覆盖间隔很久后续聊、增长超过一页、首次长回合、断线重连、已加载旧页再刷新；历史无中间缺口、无错误的“已全部加载”，加载时视口稳定；账号、空间和对话间缓存不串用。

## 3. 降低 Deployment 状态等待的数据库开销

位置：[deployment_observer.py](../api/src/vibecanvas_api/services/deployment_observer.py)、[db.py](../api/src/vibecanvas_api/storage/db.py) 的 `short_session_scope`。

观察器约每 0.1 秒查询一次，每轮调用的短会话会新建使用 NullPool 的 AsyncEngine，建立连接后执行查询和行锁操作，再提交并释放引擎。该机制原本适合少量跨生命周期操作，放进高频等待循环会放大开销。

按代码估算，每个等待请求每秒最多约 10 轮，每轮含多条 SQL；这不是生产 QPS 或数据库瓶颈的实测结论。

建议优先用完成、审批和状态变化事件驱动等待，低频查询用于核对；数据库连接池须按事件循环正确管理，只在需要原子修改时加行锁，保留租户与用户权限上下文。

验收：测量并发等待下连接创建数、查询数和延迟；不跨事件循环误用连接，不破坏 RLS；普通同步超时仍返回 504 并只取消对应执行，Human 触发异步仍返回 202；结果落库、查询、取消、客户端断开及容量释放语义均正确。

## 4. 移出异步预览接口中的同步文件读取

位置：[previews.py](../api/src/vibecanvas_api/routes/previews.py) 的 `resolve_preview`、`_source_prefix`。

异步接口直接调用同步存储读取，部分 Office 文件会在限制范围内完整读取。慢磁盘或 NFS 可能阻塞 API 事件循环；尚未实测生产阻塞程度。

建议将读取和同步解析交给有并发上限的线程执行，保留文件大小限制、安全路径检查以及读取前后的 revision 校验。

验收：模拟慢文件系统时，无关 API 请求仍能及时处理；预览类型、大小限制、版本冲突报错和访问权限不变。

## 5. 对齐 Python 版本声明与实际运行要求

位置：[API pyproject.toml](../api/pyproject.toml)、[authorization/types.py](../api/src/vibecanvas_api/authorization/types.py)、[sync_python_env.sh](../scripts/sync_python_env.sh)。

API 声明支持 Python >=3.10，但使用 Python 3.11 引入的 `enum.StrEnum` 和 `asyncio.timeout`；当前安装环境实际固定为 3.11.17。

建议对齐最低支持版本、分类标签、安装说明及 CI。引擎的版本要求应单独核实，不能仅凭 API 的依赖推断。

验收：不支持的环境在安装阶段得到明确提示；本机安装、容器、CI 和文档一致。不能假定所有 Python 3.10 环境都会安装成功后才报错，依赖解析也可能先拒绝。

## 6. 明确 Redis 故障时的 QPS 限流策略

位置：[rate_limit.py](../api/src/vibecanvas_api/services/rate_limit.py)。

当前 Redis 操作异常时返回允许调用，属于已有的 best-effort 策略，不是已确认的意外放行漏洞。但故障期间用户配置的 QPS 不能得到保证，需明确对外语义和观测方式。实现是 INCR + EXPIRE 固定窗口，与代码中的 token bucket 命名不符，并存在无用变量。

建议先确定故障时允许、拒绝或降级的产品策略，再统一实现、提示和监控；将算法命名改为实际实现，不为此次优化额外引入复杂限流框架。

验收：覆盖正常限流、Redis 故障及恢复；策略可观察且与文档一致；不改变用户手动配置的 worker 并发限制语义。

## 7. 明确 draw.io 导出的外部数据边界

位置：[drawio-export.ts](../web/src/pages/chat/preview/drawio-export.ts)。

默认导出路径创建 `embed.diagrams.net` 的 iframe，并通过 postMessage 将完整 XML 交给该外部来源页面；默认外部编辑器为 `app.diagrams.net`，地址可配置。此发现表示外部页面代码能读取 XML，不证明数据已被第三方服务器保存或泄露。

建议普通导出使用自托管渲染器或现有服务端 draw.io 导出能力；用户主动选择“打开外部编辑器”应作为独立、明确的数据边界。

验收：普通导出不向第三方页面交付源 XML，格式与效果保持；明确外部编辑器行为；仍执行原有资源权限检查。

## 8. 统一历史状态管理

主对话页面自行处理历史保留、分页及检查点，侧边栏和画布使用共享 hook，同类修复容易遗漏某个入口。

建议将历史窗口、检查点、覆盖范围、去重及请求顺序收敛到一套状态实现，页面只负责展示和视口交互。与第 2 项配合实施，不把它重复计作另一项已复现故障。

验收：主页面、插件侧边栏、画布对话共用核心逻辑，分别完成真实页面验证；切换对话、账号或空间时不继承错误缓存。

## 9. 按职责拆分过大的模块

审查时部分文件规模约为：sandbox/manager.py 4,616 行、routes/chats.py 4,314 行、agent_runtime/codex.py 3,129 行、ChatComposer.tsx 1,818 行、ChatPage.tsx 1,579 行。行数是维护成本的线索，不代表这些文件本身存在错误。

建议逐步按沙盒生命周期、资源准备、执行调度，对话路由编排，以及编辑框输入、附件、命令候选等职责拆分。先处理频繁修改且容易重复修复的模块，不为减少行数进行整体重写。

验收：模块边界和依赖方向清楚，既有行为及测试保持，不把重复逻辑复制到多个新文件；每次拆分规模可审查，不引入新的兼容层或框架。

## 10. 删除仅用于适配测试替身的生产分支

## 实施记录

### 第 1 项：首批本地修改

已限制压缩上传的读取量（与 `max_bundle_bytes` 使用同一上限，超限返回 413）；ZIP 在解压前检查所有条目数量、路径、重复文件、加密标志以及声明大小，并限制实际读取字节数。条目数量包含目录，避免以大量空目录绕过数量限制。保留原有内容和安全校验。

新增 `api/tests/test_skill_bundle_limits.py`。9 项独立测试通过；Ruff 和 diff 空白检查通过。仓库常规 pytest 入口在 root 下触发临时 PostgreSQL 初始化失败，尚未作为完整集成验证通过。独立测试通过隔离测试文件运行，仍使用当前工作树代码。尚未部署，后续需补损坏、加密包与正常上传发布的集成及真实服务验证。

### 第 2、8 项：历史窗口与共享状态

主页面已改为使用 `useConversationHistory`，删除重复的保留、检查点和分页逻辑。窗口保存分页覆盖区间和消息顺序位置，旧缓存与新页不连续时保留加载入口；较旧响应不能降低已知总量。覆盖区间按请求实际分页范围计算，不能把隐藏控制消息当作未加载缺口。

已添加 1–30 与 71–100 两段历史补齐、过期响应及隐藏控制消息的回归用例。窗口合并与 hook 回归共 12 项通过，包含隐藏消息用例。主页面与合并逻辑 ESLint 通过。仍需核对 HITL 合成消息的分页边界及顺序，完成类型检查和三个入口的真实页面验收；本项尚不能标为完成。

### 第 2 项：分页坐标与人工交互卡片

进一步核对确认：服务端分页总数包含隐藏控制记录，却曾额外加入 HITL 合成卡片数量，导致查询坐标不一致。现已保持总数为持久化记录数，并为可见持久化消息提供 `history_position`，使过滤隐藏记录后的重叠页仍能正确排序；合成卡片按时间展示，不增加分页总数。API 快照与客户端类型同步更新。

当前历史窗口及共享 hook 的 14 项前端测试通过；人工交互投影与路由分页的 12 项独立 Python 测试通过，包括隐藏行和合成卡片同时出现的情况。Ruff 通过。完整集成、类型构建及实机验证仍待完成。

### 第 3 项：API 观察器首批优化

观察器已改用 API 请求事件循环的 `session_scope` 连接池，普通状态读取不再加行锁；超时写入前重新加锁并复核终态、审批及 runtime claim。等待方式改为派发任务完成唤醒，加上最长 1 秒的核对查询；临近超时时按剩余时间唤醒。已结束的 RPC 不会引起忙循环，断开 HTTP 不会取消派发任务。

4 项独立等待测试通过（完成唤醒、等待超时、客户端取消、已结束 RPC），Ruff 通过。尚需数据库集成验证、并发连接/SQL 计数和真实服务验收；跨进程审批变化目前仍靠核对查询发现，后续需评估补齐事件通知，不能标记为完整事件驱动方案。

### 第 4、5、10 项：首批修改与验证

预览文件读取及描述符解析已通过 Starlette 有并发上限的线程池执行，授权及数据库操作仍在原请求上下文。8 项独立测试覆盖慢文件读取不阻塞事件循环、revision 冲突传递、实际请求体限制以及缺失/伪造长度头。API 最低 Python 要求与分类标签改为 3.11；未发现需要同步提高 engine 最低版本的直接证据，保留 engine 独立声明。Deployment 请求体读取移除测试专用回退，Webhook 测试改用真实 Starlette Request。

### 第 6 项：已确定故障策略

用户明确选择：已配置 QPS 时 Redis 不可用返回 503，等待恢复后重试。代码已返回稳定错误 `rate_limit_unavailable` 和 `Retry-After: 1`；未配置 QPS 不受影响。算法名称改为实际的固定窗口，删除无效 Lua 参数。5 项局部测试通过，覆盖溢出 429、未配置、不可用 503、异常 503 及恢复成功；接口文档已同步。完整调用路径及实机故障恢复验收仍待完成。

开始使用已有独立测试 PostgreSQL 集群中的专用临时数据库 `flowork_quality_review` 跑数据库集成验证；不使用线上数据库。首轮因缺少测试角色密码参数而在 fixture 初始化失败，已补参数重跑，结果待核对。

# 主应用与侧边栏视觉和交互优化清单

日期：2026-10-10。审查基线：`main`，`8b6a89c`。用途：内部产品设计、开发排期与验收。

本清单汇总主应用与浏览器侧边栏的视觉风格、编辑框、对话区、工具栏和左侧导航优化建议。方向是保持简约，采用低饱和底色、轻磨砂浮层、细腻边缘和明确的信息层级，同时改善常用操作的可发现性与一致性。

状态：**逐项实施中，进展见文末实施记录**。记录依据是当前源码、最近的主应用实机截图，以及官方产品与设计资料；不是本轮已完成的全端交互验收。“未找到入口”表示本次检查范围内未找到，实施前需确认其他入口和后端能力。以下条目均未因为写入文档而视为完成，也不代表已确定全部产品行为。

## 已确认的用户偏好与边界

- 喜欢轻微磨砂质感，保持克制的简约风，重视边缘、层次与交互专业度。
- 主应用、画布中的对话区、插件侧边栏应保持一致的操作语义，并适配不同宽度。
- Basic information 保留现有两列布局，列内对齐；复制按钮紧挨 ID。
- Goal 状态在编辑框**外部上方**，不挤占文本输入区。
- 附件展示紧凑，附件多时能横向滚动，并能操作最右侧附件的删除入口。
- 执行失败、超时应清楚返回；不得借交互优化加入业务执行的自动重试或重放。
- 优先简单、合适、资源消耗低的方案。浏览器历史缓存方案仍暂缓，不并入本次范围。

### 材质与字体实施原则

- 先完善颜色、边缘、阴影、圆角、动效的共享变量与组件，再应用到各页面，避免页面内各自硬编码。
- 磨砂质感来自底色、边缘与阴影的组合，不以大幅降低透明度替代层级设计。
- 固定侧栏背后没有变化内容时，优先靠底色和边缘呈现质感；不为装饰增加无收益的模糊层。
- 保留统一中英文字体体系，用字重、字号、行高与间距建立标题、正文、元信息层级。
- 暗色单独调校轮廓、亮边与阴影；高对比度或不支持模糊时有清晰的实色降级。
- 不做折射、持续发光或大面积动态背景；在手机和插件窄侧栏测量滚动、输入与重绘表现。

### F17：整理布局增加布局方式子菜单（用户新增）

优先级 P1，状态：已核对现有实现，待实现与实机验收。

现有 `CanvasToolbar.tsx` 的“整理布局”直接调用 `layoutWorkflowDict`；`auto-layout.ts` 用 Dagre `rankdir: LR`，按已测量节点大小从左到右排列，一次撤销可恢复。长链会形成很宽的图。目前该操作没有根据可用画布宽高选择紧凑布局。

将“整理布局”改为子菜单：

- **从左至右**：保留现有布局逻辑和分支层级。
- **适应画布**：按当前可用画布宽高组织紧凑的多行布局，避免长链无限横向展开；排列完成后调整视口，让整体结构进入可见范围。“铺满整页”表达的是充分利用画布空间，不是强制拉伸节点。

设计与实现要求：

1. 使用画布实际可用区域，考虑左右面板占用；节点按测量尺寸排列，包含展开的输出和人工审批区域。
2. 优先保持有依赖关系的节点顺序、并行/条件分支的可辨识性。长流程按结构分段换行；不能仅将节点任意装入矩形网格，或只调用 fitView 缩小原长条布局。
3. 换行后的连线不能穿过节点卡片；结合现有左右连接端口评估边的走线。实施前比较少节点、多分支、长链和混合图的渲染效果，再确定具体紧凑布局算法。
4. 只修改节点位置及必要的展示布局信息，不改变节点类型、参数、边关系和执行语义。布局作为一次可撤销操作，可保存并在重开后保持；只读版本禁用修改。
5. 明确物理限制：200 个完整节点的文字无法同时在普通屏幕上清晰阅读。先提供完整结构概览，允许放大查看详情；若要同时提高大图概览可读性，后续评估按缩放级别显示简化节点或分组折叠，不承诺全部细节一屏可读。
6. 不随每次窗口缩放或 Agent 更新自动重排用户布局；用户选择菜单时才执行。菜单支持键盘、Esc、点击外部关闭及明暗主题。

验收：小图、长链、条件与并行混合、循环配对线、断开子图，以及已有 200 节点验收图；检查无节点重叠、分支可辨、整体入屏、撤销/重做、保存重开、左右面板不同宽度和窄屏。不得以只有 fitView 或规则网格的截图替代真实复杂 Workflow 验收。

#### F17 业界方案依据与选型方向

核对官方资料后，采用“布局、视口导航、信息层级分别处理”的方向：

- [React Flow 布局指南](https://reactflow.dev/learn/layouting/layouting)：Dagre 适合较简单的分层布局，ELK 提供更多布局配置。当前 Dagre 从左到右布局继续保留；紧凑模式先验证成熟引擎能力，不自行堆叠复杂的布局补丁。
- [ELK Graph Wrapping](https://eclipse.dev/elk/reference/options/org-eclipse-elk-layered-wrapping-strategy.html)：支持将图分成若干区段，重新组织区段并处理跨区段连线，适合评估长条图利用指定绘图区的问题。该能力针对特定图形，不能仅凭文档就保证我们的所有条件/并行/循环图都适用；需实测效果、速度与集成成本。
- [yFiles 大图概览](https://docs.yworks.com/yfiles-html/dguide/view_overview/)：缩小全图会使元素变小，因此配合可导航的缩略图保留全局位置感。整体概览与局部文字阅读是两个视图尺度。
- [yFiles 分组折叠示例](https://live.yworks.com/demos/application-features/folding/)：大图可用分组折叠降低同屏信息量。此项作为后续评估方向，不在缺少业务分组语义时擅自合并节点。

推荐顺序：先比较 ELK 紧凑/分段布局与当前 Dagre 在真实验收图的表现，再接入两种布局菜单和适配视口；大图详情使用缩放与概览导航。分组折叠、按缩放级别简化节点另行评估，避免为了“铺满”一次性引入多个复杂功能。

### 按钮语义约定

- **停止**：请求停止当前执行，不暗示已撤销此前文件修改或外部操作；请求发出与后端确认停止应有区分。
- **重试**：用户明确重新执行上一次请求；不能自动发生，也不能悄悄替代发送。
- **继续**：发送新的用户指令，不与原请求重放混为一谈。
- **新对话**与**新项目**：入口、提示和所属范围清楚；多个加号不应只靠位置猜用途。
- **释放沙盒**与**删除项目**：分别说明释放运行资源和删除数据的实际影响，不使用含混的关闭图标替代含义。
- **禁用按钮**：空草稿等显然情况保持简单；历史未就绪、只读、上传未完成、模型不可用等阻塞应有明确原因。
- 菜单支持点击外部、Esc 关闭与键盘导航；常用功能有可见入口，右键和快捷键作为补充。

### 统一体系应如何组织

采用四层结构，沿用现有 React/Tailwind/组件基础，不替换框架：

1. **语义变量**：`index.css` 和 Tailwind 映射承担表面、文字、边界、焦点、状态、资源身份、阴影、圆角与动效。亮暗模式共用变量名称，分别提供值。
2. **基础组件**：现有 Button/Input/Select/Tabs/Dialog/Sheet/Menu/Tooltip/Status/AsyncState/CopyButton 统一所有状态；增加的变体服务真实场景，避免不断传散落的覆盖类。
3. **页面模式**：沿用列表外壳、详情外壳、分组与属性组件；增加或完善必要的表单行、日志行和警告提示复用。对话、画布、文件预览保留各自布局模式，共享底层语言。
4. **页面组合**：页面负责内容、权限和业务动作，尽量不自行决定一套字色/边框/字号。第三方控件通过共享适配器读取主题，不在每页独立配色。

统一不等于所有页面使用同样布局：管理列表需要密集浏览，聊天需要阅读留白，画布需要紧凑操作，预览需要尊重原文件。用默认、紧凑、阅读三类**有限且有说明的密度**表达差异，而不是每页随意改变间距。

### 明暗模式完整适配要求

- 保持 `light`、`dark`、`system` 三种选择。显式选择优先；跟随系统时响应系统变化，跨窗口与插件同步行为明确。
- 根节点、浏览器 `color-scheme`、首屏骨架、图标、favicon 和浏览器主题色一起核对；避免刷新或懒加载阶段闪现错误主题。
- 组件状态至少覆盖 default、hover、active、focus、selected、disabled、read-only、loading、error，不能只验默认截图。
- 弹窗、下拉菜单、Tooltip、Toast 等 Portal 外层要跟随主题；检查层级、遮罩叠加和磨砂后实际可读性。
- 图表、AG Grid、CodeMirror、工作簿、xterm、React Flow 分别有显式适配路径；主题切换不得丢失草稿、表格状态、画布视口或终端连接。
- 建议以普通文字 4.5:1、大号文字 3:1、关键控件/图形边界 3:1 作为验收目标；这些是待测目标，不是目前已通过的结论。透明表面需对实际合成背景测量。
- PDF 纸张、图片/视频、网页、图表文件与 HTML 成果属于内容。应用外壳换肤不应篡改作品本色；可提供明确的阅读背景选项，不能默默反色。
- 高对比度、减少动效、不支持模糊及触屏环境下仍能完成操作；不靠颜色或悬停单独传达状态和动作。

3. **优先修主题缺口**：任务结果、冲突警告、数据表、终端先适配；第三方控件通过共享适配层处理。主题修复不改业务执行和同步协议。
4. **迁移页面族**：先选对话、任务详情、设置作为样板，再扩展到各管理列表/详情、画布、预览、认证/分享/插件独立入口。每批只处理有限页面，减少同时改动造成的回归。
5. **扩展现有守卫**：在现有 `audit-visual-system.mjs` 上增加有针对性的检查，允许有理由的品牌/文档内容例外；新增违规阻止进入，旧问题按清单逐步消化，不用大范围忽略掩盖差异。

### 必须遵守的实现规则

| 编号 | 规则 | 在此次改造中的应用 |
| --- | --- | --- |
| C01 | 最小充分实现 | 改主题优先改共享 token 和现有组件；不新增主题服务、万能配置平台或事件总线 |
| C02 | 优先可读性 | 使用业务含义清楚的名字和直接控制流；必要时提前返回；避免多层三元表达式、巨大 JSX 和为了少几行而压缩逻辑 |
| C03 | 一个状态有一个权威来源 | 服务端资源继续由现有查询层管理，临时界面状态放组件或现有 store；可推导的值不再复制一份 state，不能靠多个 Effect 相互修正 |
| C04 | 复用已有能力 | 修改前查现有布局、状态、表单、主题和数据访问组件；只有已有抽象确实不适合时才新增，并说明职责差异 |
| C05 | 按真实重复抽象 | 样式相似不等于业务相同；不为假想未来需求设计泛型工厂、插件注册机制或大量可选开关。少量清晰重复可以暂时保留 |
| C06 | 职责清楚且入口少 | 页面组合业务内容，组件负责展示，hook 管理确有复用价值的交互，适配器处理第三方接口；不为每个一行表达式创建文件或 hook |
| C07 | 错误保持真实 | 不用 `catch` 后返回空列表、成功态或默认值掩盖失败；只在能处理或需要补充上下文的边界捕获，向上保留错误类型和可操作说明 |
| C08 | 不擅自重试执行 | 业务调用失败就返回错误，超时就返回超时，异步任务提供状态/结果查询；不加自动再次投递、重跑或副作用重放。连接恢复、只读补读与业务重试分开定义，不能借前者重发后者 |
| C09 | 校验集中在真实边界 | 外部输入、API 响应、跨窗口/插件消息在契约边界校验；内部已校验数据依类型和明确不变量处理，不每层再猜字段、补默认值或兼容未知格式 |
| C10 | 不提前优化 | 不默认到处加 `memo`、`useMemo`、缓存、节流、锁或状态机；有性能证据、接口要求或实际并发问题再加，并说明收益和生命周期 |
| C11 | 资源归属明确 | 谁创建监听、定时器、连接或第三方实例，谁负责清理；保留必要的取消、清理和竞态处理，但不叠加多个重复的超时/恢复控制器 |
| C12 | 删除真实冗余 | 搜索引用并核对动态入口后删除不用的分支、旧样式和废弃参数；同次替换完成后清理旧实现，不无限保留双轨兼容 |
| C13 | 注释解释原因 | 注释说明非直观约束、权衡和协议，不重复代码字面含义；类型、变量、公共接口和国际化文案跟随现有规范 |
| C14 | 小步改造与验证 | 按页面族提交可审查的改动；不混入无关格式化或架构重写。修复测试检查真实行为，不为迁就错误实现改断言或关闭检查 |

### 如何区分必要校验与过度防御

| 保留的必要处理 | 应避免的复杂化 |
| --- | --- |
| 权限、租户隔离、来源验证、输入契约与文件访问边界 | 以精简为名删掉授权或跨来源校验 |
| 对真实超时返回明确错误，对外部连接/订阅正确清理 | 为掩盖未知根因增加多层重试、恢复循环和兜底执行 |
| 处理已存在的多窗口竞争、过期响应与组件卸载 | 没有触发路径和需求，却增加去重槽、进程轮换或完整调度框架 |
| 保存失败保留用户草稿，读取失败区分旧数据与错误 | 把失败伪装成无数据或成功，清空历史让用户自行恢复 |
| 不支持磨砂时回退为可读实色，未知业务状态明确呈现 | 给任意异常套默认值，吞掉错误或猜测执行已成功 |

“减少防御性代码”不是取消正确性与安全边界。每个新增分支应能解释它对应的真实输入、契约或故障场景；无法解释的假想分支先不添加。

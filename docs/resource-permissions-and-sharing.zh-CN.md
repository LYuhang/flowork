本文用于逐类讨论 Flowork 的资源归属、访问权限和分享方式。先记录当前代码中的资源清单及权限现状，再逐项补充产品决策，作为后续实现和验收的依据。

## 当前空间隔离规则（2026-10-04，优先于下文历史记录）

个人空间与公司空间是两个独立的权限上下文。公司内的个人成员身份不是其独立个人空间；部门是公司内的授权分组，不另建租户。

- 公司内创建的资源归公司，默认仍按创建者权限访问，不自动共享给全员。
- 公司资源分享给某个邮箱，是授权该用户在该公司的成员身份。直接用户、部门、公司三种授权均只能在该公司空间使用。
- 个人空间只能发现、打开和使用个人资源及其他个人空间显式分享的资源；公司资源不会混入。公司空间也不能访问个人分享或其他公司的资源。
- 空间边界在宿主机统一授权层执行，覆盖列表、直接 ID、文件、签名访问、Agent/CLI 和 Skill 包读取；前端筛选不能代替鉴权。
- 切换空间保留分享关系和 Skill 安装选择，但只向当前空间的 Agent 挂载可用包；退出公司或撤权继续触发权限及安装失效处理。
- Task/Deployment 后台执行保持其绑定的服务账号与所属空间，浏览器切换不改变已运行实例的身份。
- 不引入兼容旧跨公司聚合逻辑的开关，也不复制资源。既有分享数据按资源归属解释即可。

本次空间边界修复已部署，数据库回归、双账号 HTTP 和浏览器切换验收通过；真实 Agent 的列表、按 ID 查询及 Skill/Knowledge 文件下载补测均通过。下文较早的跨空间公司资源测试仅为历史证据，不能作为本规则通过的依据。

## 当前开发顺序与底层契约

按用户要求，自底向上推进；先固定权限契约和验证边界，再接入业务入口及界面。复用现有授权服务、OpenFGA 和数据库 RLS，不再引入另一套权限引擎。

1. **身份与归属**：分别记录真实操作者、资源所属组织、运行服务账号。访问共享资源不切换成资源所有者身份。
2. **动作与角色**：统一资源动作注册表、角色映射和关系模型；可编辑与可执行独立，可组合。管理权限不等于转移所有权或取得模型密钥。
3. **共享依赖**：明确哪些版本、文件随父资源授权，哪些历史、凭据、关联资源必须单独检查；禁止依据任意资源 ID 扩大数据库访问范围。
4. **统一入口**：网页 API、CLI、Agent、后台任务和文件加载复用同一宿主机检查；列表能发现资源不等于有权执行所有操作。
5. **授权一致性**：授权变更记录与业务修改同事务保存，外部关系更新失败可重试；撤销、成员退出、账号禁用之后重新验证，不以残留挂载或旧依赖绕过检查。
6. **逐层验收**：先测底层允许和拒绝矩阵，再验证每种资源的入口，最后部署到真实服务，用两个账号完成分享、组合角色、降级、撤销及直接 ID/路径访问验收。

底层对外只保留三类职责：判断资源动作是否允许、发现有权访问的资源、修改分享关系。资源特有规则留在对应业务策略中，不分散到前端按钮或 Agent prompt 中充当安全边界。

Workflow 分享不能开放他人的数据库执行历史。接收者仅能按权限获取自己发起的执行反馈，指定审批人按审批范围访问。shared-workflow-run-live.json 已完成两账号分别运行、各读自己记录、互读拒绝的实机检查。

本轮代码核对日期：2026-10-04。当前现状以存储模型、权限模型和相关接口为依据，不等同于已完成所有权限路径的实机审计。

## 需要单独明确范围的附属内容

附属内容通常不是顶层产品入口，但分享主资源时必须明确是否覆盖这些内容。

| 内容 | 讨论重点 |
| --- | --- |
| 版本和草稿 | 授权是针对整个资源、某个大版本、固定子版本，还是发布时的快照；是否包含草稿和未来版本 |
| 执行历史 | 是否包含历史调用、节点输入输出、错误、日志、Trace；是否只允许查看自己的执行 |
| 人工审批 | 查看审批内容与点击通过、驳回是否采用独立授权；资源分享与指定审批人如何配合 |
| 附件和生成文件 | 分享文字是否同时允许访问引用文件；允许预览、下载和修改的范围分别是什么 |
| 对话输入审计 | 用户可见消息和实际发送给 Agent 的输入记录是否采用不同访问范围 |
| 关联资源 | 查看 Task 或 Deployment 是否允许打开对应 Workflow 快照；是否进一步允许访问 Workflow 本体 |

例如，“可以查看 Workflow 定义”与“可以查看它过去处理的业务数据”需要分别讨论。本文尚未决定两者必须分权，也未决定应当默认一起授权。

| 对象 | 需要区分的操作 |
| --- | --- |
| 模型连接和 LLM 凭据 | 使用模型、查看连接信息、配置连接、管理或读取密钥 |
| MCP OAuth 授权及其它 Secret | 使用已授权工具、管理授权、读取或替换凭据 |

沙盒和 Worker 仅是运行资源，不作为分享对象，不另设沙盒分享授权。持久化对象存储可随所属业务资源连带共享；平台负责分配计算资源，并根据业务资源权限访问或挂载存储。沙盒的实际复用和调度不由分享关系决定。

## 资源归属与授权对象

代码中还存在组织、用户、用户组、服务账号等对象，用于表达资源归属和授权主体。工作空间与组织之间的具体产品映射，以及个人资源和组织资源的转换规则，需要在正式设计时明确。

需讨论的授权对象包括指定用户、用户组、组织成员、服务账号，以及持有公开分享链接的访问者。公开链接当前只在特定功能中实现，不能理解为上述所有资源已经支持匿名分享。

## 用户提出的初步设计方向

以下记录用户本轮提出的方向，后续逐类细化；本轮不进行权限代码改造。

### 分享对象

显式分享需要支持指定个人用户、部门、公司等对象。现有用户、用户组和组织模型可以作为设计基础，但部门与用户组、公司与组织的产品映射尚待确定。

尚需讨论：部门是否覆盖子部门、成员加入和离开后的授权变化、是否允许跨公司分享，以及公司分享是否表示全部有效成员。不能将“支持分享给公司”直接解释为已经允许任意跨组织访问。

### 显式分享的资源范围

| 资源 | 初步方向 | 仍需细化 |
| --- | --- | --- |
| Workflow | 支持显式分享给用户、部门、公司等对象；关联对象存储连带共享 | 角色与版本细则；数据库执行历史、日志和 Trace 暂不连带分享 |
| Task | 支持显式分享 | 任务配置、执行操作、日志、结果及关联存储的权限 |
| Deployment | 支持显式分享 | 调用、管理、历史结果、Trace 及关联存储的权限 |
| Skill | 补齐显式分享，仅限 custom 资源 | custom 的判定、使用与查看内容的关系、编辑和发布权限 |
| Knowledge | 仅限 custom 资源开放显式分享 | custom 的判定、资料读取、下载、修改与发布权限 |

非 custom 的 Skill 和 Knowledge 不进入本轮新增显式分享机制；它们原有的可见性和使用规则需单独核对，不由本条推导新的开放或禁用规则。

Project 和 MCP 不支持分享。Chat 不提供原始对话的协作分享，仅支持快照分享；现有 Chat 公开快照机制见前文。

### Project 和 MCP 不分享 Chat 仅分享快照

以用户最新说明为准：Project 和 MCP 均不支持分享；Chat 仅支持快照分享，不提供原始对话的协作授权。Project 不提供快照分享入口。

Chat 快照不会授予接收者访问原 Project 文件、继续原对话或使用原运行沙盒的权限。当前对话与单条助手回复的快照机制见前文；其内容范围、链接有效期等是否需要调整，另行讨论，不因本条自动扩展。

上述产品分享范围不等于删除现有运行所需的内部授权关系。例如，MCP 的服务账号使用关系需与面向用户的资源分享入口区分。

### Storage 依附业务资源授权

Storage 暂不提供独立分享入口，也不单独向用户、部门或公司建立文件或文件夹分享关系。需要分享的文件访问随其所属业务资源设计，例如 Workflow 的关联存储，以及 Task、Deployment 的关联存储。

“依附资源”不直接规定所有接收者都能读写全部文件。哪些角色可以预览、下载、修改或删除哪些关联文件，随对应资源的权限方案一起确认。

还需明确资源边界：Task 或 Deployment 引用某个 Workflow，不意味着分享它们就自动授予原 Workflow 全部存储的访问权；是否包含固定版本快照、结果文件、运行日志等，逐项定稿。此处记录待明确的边界，不表示已经新增相应限制。

### Workflow 连带分享边界

用户已明确区分 Workflow、对象存储和沙盒，并进一步收敛本轮范围：

| 对象 | 本轮设计方向 |
| --- | --- |
| Workflow 定义和版本 | 显式分享，具体操作受角色和版本规则约束 |
| Workflow 关联的对象存储，例如持久化的 /run 文件 | 随 Workflow 连带共享，访问同一份关联文件，不按接收者复制或改为各用户独立目录 |
| 沙盒和 Worker | 仅提供运行资源，不作为分享对象，不需单独分享授权 |
| 数据库中的执行历史、日志和 Trace | 暂不纳入 Workflow 连带分享，本轮不扩展这部分分享能力 |

对象存储文件与数据库执行记录按各自边界处理。上述范围不表示删除执行记录，也不表示禁用用户正常执行时原有的结果反馈；Task、Deployment 的历史记录分享范围仍按各自资源讨论。

此前对“各用户独立 /run”的理解已撤回，不作为实现要求。

## 分享角色建议

本节是待用户确认的设计建议，不代表当前代码已全部遵循，也不替代后续各资源的具体决策。

### 角色关系

建议可读作为基础，可编辑与可执行并列，可管理包含全部权限。允许同时授予可编辑和可执行；可以向某用户、部门或公司授予角色，同一用户从不同有效授权获得的能力按并集合并。

| 操作 | 可读 viewer | 可编辑 editor | 可执行 operator | 可管理 manager |
| --- | --- | --- | --- | --- |
| 查看资源内容与配置 | 是 | 是 | 是 | 是 |
| 查看授权范围内的日志、结果和关联文件 | 是 | 是 | 是 | 是 |
| 修改资源配置或内容 | 否 | 是 | 否 | 是 |
| 手动增删改允许编辑的关联文件 | 否 | 是 | 否 | 是 |
| 发起执行或调用 | 否 | 否 | 是 | 是 |
| 操作当前资源的执行生命周期 | 否 | 否 | 是 | 是 |
| 分享、撤销分享、调整他人权限 | 否 | 否 | 否 | 是 |
| 删除整个资源 | 否 | 否 | 否 | 是 |

表中日志、结果和文件均限于已明确纳入分享范围的内容，不代表能够读取任意关联资源的数据。Workflow 数据库执行历史、日志和 Trace 已明确暂不纳入连带分享，不能由此表推导为所有角色开放这部分内容。现有 Workflow、Deployment 的 viewer 不具有 inspect_runs，而 Task 的 viewer 具有；具体实现应按各资源最终范围调整，而非直接统一放开。

可执行允许通过执行流程产生输出文件，不赋予手工修改任意文件或编辑 Workflow 的权限。具体运行逻辑可能本身具有文件写入等效果，不能将可执行误认为无副作用。

可管理允许管理当前资源，但不自动授予组织管理权限、关联资源的管理权限或读取他人凭据明文的权限。转移所有权另行决定，不自动与转分享合并。

### 各资源的角色落点

| 资源 | 可编辑的主要范围 | 可执行的主要范围 | 需进一步明确的边界 |
| --- | --- | --- | --- |
| Workflow | 修改节点、连线、配置，保存符合版本规则的新版本 | 工作流执行、节点调试、取消相应执行 | 创建 Task 或 Deployment 同时涉及目标资源创建权；关联对象存储连带共享，数据库执行历史暂不连带分享 |
| Task | 修改系统允许编辑的任务配置，维护可编辑的输入文件 | 按任务类型允许的操作执行、暂停、恢复或取消 | 批量任务仍保持一次执行语义；周期、输入、绑定版本等修改权限不随可执行授予 |
| Deployment | 修改允许编辑的部署配置 | 调用、启停及取消相应调用，具体操作逐项确认 | 会立即重建或重启实例的配置变更同时涉及编辑与执行，不因接口名叫 update 而只检查编辑 |
| custom Skill | 修改草稿、增删改文件；建议编辑权限包含发布 | 建议不单设可执行角色，可读包含读取、下载及在自身授权环境中使用内容 | 使用 Skill 不自动获得其依赖的模型、MCP 或其它资源权限 |
| custom Knowledge | 修改资料与文件；建议编辑权限包含发布 | 建议不单设可执行角色，可读包含读取、下载及在自身授权环境中使用内容 | 应用功能层面的使用许可与文件读取关系需对齐现有接口 |

Skill 和 Knowledge 建议在分享界面只显示可读、可编辑、可管理三个角色。已经允许读取或下载内容时，不宜承诺通过一个独立的“禁止使用”角色阻止接收者将内容提供给自己的 Agent。上述方案仍待用户确认。

### 分享界面建议

先选择用户、部门或公司，再配置角色。Workflow、Task、Deployment 的可编辑和可执行可以组合授予；可管理覆盖全部，避免要求用户重复勾选。部门与公司收到角色后，其成员的具体生效范围按后续成员继承规则处理。

公开 Chat 快照不使用这套协作角色；Project、MCP 不提供分享；Storage 不提供单独角色配置入口，文件操作依附所属资源的权限规则。

## 共享资源向 Agent 暴露

### 用户明确的权限原则

被分享用户的 Agent 沿用该用户自己的有效权限，包括直接授予用户，以及按最终成员规则从部门、公司获得的权限。资源被分享后，Agent 不切换成分享者或资源创建者身份，也不另行获得更高权限。

主对话和 Workflow 画布对话采用同一原则。Agent 的实际操作还受现有会话和工具范围约束；继承用户权限不表示自动启用所有工具或将所有资源装入沙盒。

### 资源发现与工具输出建议

建议复用各资源现有的 list、详情和操作命令，不新增一套专门的“共享资源 CLI”。在获准的组织访问范围内，列表同时返回用户自有及获分享的可见资源，不仅按创建者筛选。

列表与详情建议暴露资源 ID、名称、说明、资源归属、有效角色和具体可用操作。版本化资源在相应详情中明确版本。Agent 能据此选择已有资源，并在操作前知道是否可读、可编辑、可执行或可管理。列表不直接返回整份内容、文件或凭据。

当前代码已有可复用基础：Agent 资源上下文绑定用户、会话和有效身份；Workflow 的授权列表会附带有效 capabilities，读取和操作也有动作级鉴权。但尚未核对全部五类资源是否完整对齐，不能据此宣称 Skill 分享及所有 Agent 入口已经实现。

目前 Workflow 列表还受当前组织的数据库访问边界约束。跨组织分享是否开放、如何发现和访问，须在跨组织规则确定后一起实现，不能仅放宽列表筛选。

### 使用流程建议

| 资源 | Agent 如何发现和使用 |
| --- | --- |
| Workflow | 从授权列表或用户提供的引用取得 ID，读取获准的版本，并按有效权限修改或执行 |
| Task | 从授权列表取得任务，按权限查看详情、日志、结果及操作执行；任务类型自身的限制仍生效 |
| Deployment | 从授权列表取得部署，按权限查看、调用或管理；平台 CLI 使用当前用户鉴权，不要求把分享者的 API key 给 Agent |
| custom Skill | 共享包与自有包进入同一授权 Skill 解析和 /skills 挂载链路；同步已有沙盒中的版本或补充缺失目录时复用 refresh 机制 |
| custom Knowledge | 从授权列表发现，按权限下载或访问所需资料，沿用现有下载和文件处理方式 |
| 关联存储 | 通过所属资源的文件入口访问，只允许该角色和分享范围内的路径与操作，不开放分享者其它文件 |

Skill 可见、授权使用与已加载到某次会话是不同状态，但共享来源不应成为挂载障碍。用户已明确共享 Skill 包同样需要挂载到 /skills；沿用自有 Skill 的现有解析、挂载和同步机制，不另设一套仅能列出却不能使用的共享包流程。Knowledge 文件和 Workflow 内容仍按需读取，不因此全量注入 system prompt。

### 共享 Skill 包挂载要求

用户明确要求：获分享且具有使用权限的 custom Skill 包，应与自有 Skill 一样进入 Agent 沙盒的 /skills 目录。仅让列表显示共享 Skill 不算完成。

代码核对到的现有基础：runtime_skill_descriptors 根据当前主体的 Action.USE 取得可用 Skill，生成描述和路径；hydrate_runtime_skills 将获准的已发布版本文件装载到宿主机目录；沙盒以只读方式暴露 /skills。Chat 当前路径为 /skills/<会话范围>/<Skill ID>，Workflow 执行资源另有包含 Skill ID 和版本哈希的路径。继续复用这些约定，不按共享者名称或包名称另建一套路径规则。

共享包需要补齐以下接入点：

- 宿主机使用接收者身份，解析其直接、部门或公司授权，取得有权使用的共享 Skill 和发布版本。
- 通过所属资源的受控读取链路获取完整包文件；当前装载函数使用单一 tenant_id，跨个人或组织资源不能只改授权列表而忽略实际取包范围。
- 描述中的路径与实际 /skills 文件一致，包内脚本和辅助文件一并可用；不同所有者的同名 Skill 继续按资源 ID 区分。
- 挂载保持只读。可编辑权限通过现有草稿、发布接口处理，不将沙盒里的包目录变成对发布资源的直接写入口。
- 已有对话中的新分享或发布更新，复用 refresh 和现有同步链路使目录可用；refresh 不修改平台 Skill，也不能绕过宿主机授权。
- 主对话、画布对话及 Workflow SubAgent 的资源解析与挂载分别验收。只读挂载不会自动授权 Skill 引用的其它资源。

当前具备装载机制，但 Skill 的通用分享模型及相关接入尚未完成，因此不能宣称共享包挂载已端到端支持。

### 鉴权与权限变化建议

用户明确：Agent 权限完全复用宿主机侧已有的用户资源鉴权方案，如现有 Agent 操作 Workflow 的链路，不新增 Agent 专属权限体系，也不在沙盒中维护另一套分享关系。

调用链为 Agent → 现有 CLI 或工具 → 宿主机校验已认证的当前用户身份、目标资源及具体操作 → 执行获准操作。身份取自可信会话或已验证的运行授权，不接受 Agent 自行声明分享者身份。前端、CLI 和 Agent 工具使用相同的权限规则。提示和列表中的 capabilities 帮助 Agent 选择正确操作，不承担授权判定。

宿主机负责将新增分享、部门和公司授权纳入有效权限，并在列表、详情、修改、执行及关联文件访问入口执行检查。沙盒只承载获准的运行操作。已挂载文件的访问沿用宿主机控制的挂载范围与读写能力，撤销和缓存处理仍需核对，不因此引入第二套沙盒权限系统。

新增或撤销分享、部门成员变化后，后续列表和操作应按生效后的权限处理，不依赖开启新对话或重启沙盒。撤销后不得继续从服务端读取或更新资源；已经下载、挂载或进入对话上下文的副本无法视为自动收回，已有 Skill 挂载和文件缓存的处置需要在实现时单独核对。

共享资源不自动共享其所有者的模型连接、模型密钥、MCP OAuth 授权或其它未经授权的关联资源。Agent 发起操作的用户身份与已创建 Task、Deployment 的后台运行凭据是两层问题，模型资源采用下节规则。

验收需覆盖同一用户经前端与 Agent 获得一致结果、部门或公司分享的资源可被 list 发现、已有会话获得新授权、撤销后的后续访问被拒绝，以及不会因已知资源 ID 或直接访问存储路径绕过权限。

## flowork-cli 全量资源操作要求

用户明确：Agent 通过 flowork-cli 操作的各种资源，全部遵循本设计的授权与分享规则。该要求不局限于 Workflow，也不以是否显示前端按钮为依据；具体操作仍由宿主机统一鉴权，不在 CLI 或 Agent 中建立另一套权限判定。

| 操作类别 | 必须满足的要求 |
| --- | --- |
| 列表与资源发现 | 仅返回当前用户获准发现的资源，纳入有效的直接、部门、公司分享；根据权限决定可返回的内容与操作说明 |
| 详情、版本、下载及文件读取 | 按目标资源和读取动作检查权限；知道 ID、路径或版本号不能绕过检查 |
| 创建资源 | 检查目标工作空间的创建权限及所引用资源、运行凭据的使用权限；不能借创建操作自动复制他人的授权 |
| 修改、上传、发布和删除 | 按最终角色规则检查具体操作，保留版本冲突保护及资源自身的生命周期限制 |
| Workflow 和节点执行 | 检查执行者对目标 Workflow 的执行权限及其选用模型连接的使用权限 |
| Task 和 Deployment 操作 | 检查操作者对原实例的权限；已有实例继续使用原来绑定的模型凭据及运行资源，后续部署调用也不切换为操作者资源 |
| status、history、logs、result 等观测操作 | 按资源类型及记录访问范围鉴权，不能因允许执行就默认开放所有数据库历史记录；正常执行反馈按已确定的规则保留 |
| Skill refresh 和挂载 | 在宿主机检查共享包使用权限，读取正确归属和版本的包；不把 refresh 当作修改或发布授权 |
| 关联对象存储 | 依附所属业务资源和具体文件操作鉴权，不扩大为对分享者全部存储的访问权 |

Project、MCP 不提供分享，Chat 仅支持快照，Skill 和 Knowledge 仅 custom 可显式分享，这些规则在 CLI 入口同样适用。沙盒仍只是运行资源，不增加沙盒分享角色。

分享关系、成员关系或角色变化后，后续命令使用生效后的权限；CLI 返回清楚的错误，不伪装成成功、不自动切换分享者身份。已挂载或下载的文件仍按前文所述的挂载与缓存边界处理，不能将沙盒 bash 读取误认为每次都经过 CLI 鉴权。

实施时需逐条盘点实际存在的资源命令与其宿主机处理入口，检查列表和已知 ID 直接访问、普通接口与批量或多步修改入口是否一致。本文不是声明当前全部命令已通过验收，也不要求为每类资源新增所有表中命令。

验收需使用至少两个用户，以自有资源、直接分享、部门分享、公司分享和未授权资源覆盖正反例；同一操作在前端与 CLI 的结果应一致。还需在已有对话中验证授权新增、降级、撤销，验证共享 Skill 实际可挂载，以及操作者变化不改变已有 Task、Deployment 的资源绑定。

## 模型资源不连带分享

用户认可上一轮提出的运行凭据方案，并明确模型资源不能被关联分享。分享 Workflow 不授予接收者使用创建者模型连接、API key 或模型额度的权限；不能仅隐藏密钥明文，却仍默认允许消耗创建者额度。

| 场景 | 模型连接与凭据归属 |
| --- | --- |
| 接收者通过画布或 Agent 直接执行共享 Workflow，包括节点调试 | 使用执行者自己有权使用的模型连接，不自动借用分享者的连接 |
| 接收者操作已创建的 Task | 使用 Task 已绑定的运行凭据；操作权限仍由宿主机检查 |
| 接收者调用已创建的 Deployment | 使用 Deployment 已绑定的运行凭据；不授予调用者在其它场景使用该凭据的权限 |

例如 A 有 api1，B 没有：B 可按授权查看或编辑 A 分享的 Workflow，但执行前需要提供自己获准的模型连接。宿主机检查所需连接，缺失时明确提示选择或配置，不回退到 A 的 api1。替换连接应作用于本次执行上下文，不为了让 B 运行而改写共享 Workflow 定义，也不静默更换模型。

用户进一步明确：已运行的 Task、Deployment 继续使用原用户为实例绑定的模型凭据及运行资源；被分享用户操作原实例或发起后续 Deployment 调用，不自动切换为该用户的资源。分享不改变已有实例的资源绑定和费用归属。

Task 和 Deployment 的后台运行继续消耗其绑定凭据的额度。这是对获准任务或服务的运行访问，不是向接收者发放通用模型连接权限。新建实例时如何选择和验证运行凭据，需要在对应创建流程中对齐。

运行面板如何展示连接映射、是否记住个人选择、多模型连接如何分别匹配等交互细节仍待细化。模型连接若未来需要单独授权，必须明确授予，不由业务资源分享推导；本轮不新增模型连接分享入口。

上述为设计结论，尚未据此调整代码或完成实机验收。

## 逐类讨论顺序

根据本轮范围，建议先讨论明确需要显式分享的五类资源，再统一核对 Storage 的从属规则，最后核对不分享资源及 Chat 快照的边界。

| 顺序 | 资源 | 首先需要回答的问题 | 状态 |
| --- | --- | --- | --- |
| 1 | Workflow | 查看、编辑、执行、部署及版本权限如何划分 | 关联对象存储共享；沙盒不分享；数据库执行历史暂不连带分享 |
| 2 | Task | 谁能查看任务、启动或取消执行、修改定时配置、读取结果及审批 | 分享方向已提出，细则待讨论 |
| 3 | Deployment | 调用者与管理者如何区分；结果、Trace 和关联 Workflow 可见范围是什么 | 分享方向已提出，细则待讨论 |
| 4 | Skill | custom 资源的使用、查看文件、编辑草稿和发布权限如何划分 | 仅 custom，细则待讨论 |
| 5 | Knowledge | custom 资源的整体与文件授权粒度；读取、下载、修改及发布如何划分 | 仅 custom，细则待讨论 |
| 6 | Storage | 随各业务资源开放哪些文件操作，如何处理跨资源关联与撤销 | 暂不独立分享，从属规则待讨论 |
| 7 | Project | 核对无资源分享或 Project 快照分享入口，关联 Chat 的快照不开放原项目 | 不支持分享 |
| 8 | Chat | 核对快照内容与原始对话的边界；现有快照细则是否需要调整 | 仅支持快照分享 |
| 9 | MCP | 核对无产品分享入口，工具执行所需内部授权与用户分享分开处理 | 不支持分享 |
| 补充 | 凭据、模板、运行环境及组织管理 | 主资源规则确定后，核对依赖授权和管理权限 | 待讨论 |

每类资源分别明确资源归属、授权对象、允许操作、版本与附属内容范围、分享形式，以及撤销授权对已有访问和运行中任务的影响。是否允许复制或导出，也应显式记录。

## 自底向上的实施基线（2026-10-04）

用户已要求完成实现、更新真实服务并使用两个账号全面验收，并进一步要求从底层权限框架向上开发。本节将前文讨论收敛为实施基线；前文“本轮不实现”等描述仅记录当时阶段，不再表示当前任务停止在讨论阶段。以下未由用户逐项指定的细节是实现采用的明确默认规则，不宣称用户已逐项确认。

### 第一层：身份、归属与关系

- 身份只取自已认证用户或受控后台运行授权。网页、CLI、Agent 共用宿主机校验，不接受调用参数指定资源所有者身份。
- 资源的所属组织与创建者不因分享发生变化。跨个人账号分享不意味着加入对方组织，也不授予该组织其它资源访问权。
- 公司对应组织的有效成员；部门对应已有 Group，支持本部门及包含子部门两种成员范围。公司授权需覆盖有效 owner/admin/member，不能因管理者未另写 member 关系而漏掉他们；guest 不自动加入公司分享范围。
- 显式用户授权、部门授权、公司授权取并集。撤销某一路授权后，其它有效来源仍生效；前端必须展示这一事实。
- 资源创建者的管理能力属于结构关系，不允许通过撤销分享移除。授予 manager 只管理该资源，不等于转移所有权或授予组织管理员。

### 第二层：统一能力矩阵

| 能力 | viewer | editor | operator | manager |
| --- | --- | --- | --- | --- |
| 读取资源和授权范围内的版本、文件 | 是 | 是 | 是 | 是 |
| 修改配置、草稿、可编辑文件；发布内容 | 否 | 是 | 否 | 是 |
| 执行及允许的启停、取消操作 | 否 | 否 | 是 | 是 |
| 修改分享关系、删除整个资源 | 否 | 否 | 否 | 是 |

Workflow、Task、Deployment 使用四种角色，editor 与 operator 可组合。custom Skill、custom Knowledge 使用 viewer、editor、manager；读取包或资料即包含在自身授权环境中使用，不额外设置 operator。内部服务账号 consumer 关系仍用于运行依赖，不能成为面向用户的额外分享角色或绕过资源授权。

统一关系和 Action 的注册表必须与 OpenFGA 模型一致。路由和 UI 从注册表读取允许角色，不再各自维护重复角色数组。能力只说明授权，不替代版本不可编辑、批量任务只能执行一次等业务条件。

### 第三层：资源边界与运行上下文

| 对象 | 权限边界 |
| --- | --- |
| Workflow 定义 | 分享整个资源及版本；旧子版本仍只读 |
| Workflow /run | 同一份持久化文件，读写按角色，不复制为接收者私有目录 |
| Workflow 数据库历史、日志、Trace | 分享不授予读取他人执行记录；发起者仍能获取自己的执行反馈 |
| Task、Deployment | 配置、实例历史及关联文件按该资源授权；不自动授权原 Workflow 全部资源 |
| Task、Deployment 固定 Workflow 快照 | 可在所属实例授权范围内读取，不能借此编辑原 Workflow 或读取其 /run |
| Skill、Knowledge | 仅 custom 可显式分享；内容、草稿、发布版本和文件遵循父资源权限 |
| Project、MCP | 无显式分享；现有内部运行授权不作为用户分享入口 |
| Chat | 仅已保存内容的快照分享，不开放原会话、附件、项目文件或沙盒 |
| 沙盒、Worker | 计算资源，不建立分享关系 |
| 模型连接、密钥 | 不随资源分享。共享 Workflow 直接执行检查执行者的连接；已有 Task、Deployment 保持原绑定 |

/run 内已有输出文件按文件共享处理；“数据库历史不共享”不保证共享文件不含运行内容。内部凭据不得写入可共享目录。创建新 Task、Deployment 必须检查创建者及其运行依赖，不得借实例复制自动获得原创建者凭据。

### 第四层：统一读取与授权变更

列表发现与详情读取必须走同一资源授权范围；跨组织访问先定位受控资源，再在资源所属组织读取，不全局关闭 RLS，也不临时将用户提升为资源所有者。关联文件、版本、下载、预览、Skill 挂载沿用同一资源范围。

授权变更继续使用现有变更记录、同步及撤销保护机制。授权尚未成功生效时不得向用户伪报成功；撤销后的后续服务端请求必须拒绝。已经下载或进入模型上下文的内容不能撤回。Skill refresh 每次重新检查权限，不能用旧描述继续下载被撤销的包。

### 开发与验收顺序

采用逐层验收，不按页面逐个堆叠权限判断。第一、二层通过后再扩展资源业务和界面；已有界面改动留在开发分支，不以按钮可用作为权限能力完成的依据。

### 持久任务的跨组织依赖：实现边界补充

2026-10-04 进一步核对发现，依赖不仅用于运行前读取，还参与 Task/Deployment 创建、删除、刷新依赖及后台授权投影校准。service_account_edges、delegate_new_resources 和投影扫描都将 consumer 边归为账号组织；AuthzMutationCoordinator 明确拒绝其它组织的边。不能仅扩大 SkillsRepo 的读取范围。

后续实现采用如下约束，沿用现有框架而非另建权限引擎：

- 依赖记录需要明确区分账号所属组织与资源所属组织。资源归属必须由宿主机读取真实资源确定，不接受用户或 Workflow JSON 指定；已有本组织依赖可一次性回填，不保留两套长期读取规则。
- 账号与依赖绑定仍存于账号组织；对 Skill 的 consumer 授权边及对应投影归资源组织。授权变更按所属组织分组，业务绑定与持久化变更意图须保持同一数据库事务，提交后按组织应用；失败不能向用户伪报部署或创建成功。
- 绑定时检查原实例创建者可使用该 Skill，运行时检查有效账号、未撤销的明确依赖、Skill 及固定版本访问权限。跨组织依赖还必须受原绑定用户的当前分享权限约束，防止撤销分享后通过残留 consumer 边继续读取。
- Task/Deployment 继续使用原实例的账号、模型连接与费用归属。这里的原绑定用户是实例创建者，不是 Skill 所有者，也不是后来调用实例的分享接收者。
- 创建、删除、依赖刷新、后台投影校准、快照解析、文件加载和租约清理一起覆盖。验收需包括有效授权、撤销分享、禁用账号、撤销依赖、旧版本固定、并发刷新和投影失败后重试，且失败重试不得恢复已撤销授权。

这一节是根据当前代码约束明确的实施方案，尚未完成相应数据库和授权投影改造。此前“暂不需要增加兼容字段”不排除新增资源归属字段；不新增兼容路径。

### 权限可见性与交互规范（2026-10-04）

页面应使用后端返回的有效 capabilities 控制交互，不能从单一角色名称推断全部能力。编辑与执行独立；多来源权限取并集。标题旁展示只读、可编辑、可执行、可编辑·可执行或可管理；仅在确有所有权依据时展示所有者。权限来源只展示调用者允许查看的信息。

- Workflow：只读时仍允许平移、缩放、临时自动布局、查看版本和 Inspector；禁止拖动修改位置、连线、粘贴、删除、保存及编辑属性，快捷键和右键入口也遵守权限。历史子版本只读应说明版本原因，并提供进入同一大版本最新版的入口。执行按钮独立检查执行权限，创建任务/部署还检查对应创建权限。上下文对话沿用仅可编辑画布启用的约定。
- Skill、Knowledge：查看者仍能浏览文件、预览、查看版本和下载；主要编辑入口保留但置灰，并显示可理解的原因。文件增删改与发布按具体能力控制；历史版本不能直接编辑。不得为查看者请求仅编辑者可访问的草稿。
- Task、Deployment：配置修改与运行操作分别鉴权；固定字段明确说明不可变原因；保存若会触发重新部署，必须明确动作并检查所需的组合权限。
- 分享管理与所有权分开；删除、转移所有权按具体能力单独判断。非管理者仅展示自己的权限，不因为进入权限说明而泄露完整成员列表。
- 权限降级后根据最新能力关闭编辑入口；已有未提交内容尽量保留，保存失败须提示权限变化。刷新权限不能继续主动读取受限编辑数据。
- 分享 Workflow 不授予他人的对话、执行历史、Trace 或模型凭据；关联文件的展示仍遵守既定共享/私有目录边界。

验收需用两个真实账号覆盖：角色并集、只读按钮/快捷键/右键、历史版本、编辑与执行独立、打开页面后撤权、已打开弹窗的操作与服务端拒绝、资源来源链接、移动端禁用原因可见性。当前这里只记录规范，不代表全部实现或上线。

首批页面修正：Skill/Knowledge 主要编辑按钮保留并按权限与版本置灰；Knowledge 刷新只在当前仍有编辑权限时读取草稿，编辑状态同时绑定当前权限和最新版本。其余资源标签、权限来源及实时降权全入口仍待完成。


### 授权持久化约束（2026-10-04）

沿用关系型授权（ReBAC）：PostgreSQL 保存授权变更意图、审计、同步状态及每条关系的单调版本；OpenFGA 执行关系计算。用户/部门/公司使用稳定 ID，邮箱仅用于查找。有效 capabilities 由后端计算，不能存成另一份授权真相。

现有 authz_edge_revisions 以组织、资源类型/ID、关系、主体类型/ID、主体关系构成复合主键；authz_mutations 保存操作者、意图、版本、幂等键、状态、重试次数及时间。数据库约束限制操作与目标状态一致、撤销保护状态合法。同组织幂等键唯一，新版本防止旧同步任务覆盖新授权。撤销意图提交后，即使 OpenFGA 同步失败也由 RevocationGuard 拒绝访问，后台重试恢复一致性。

shared_resource_projections 仅用于发现资源所属组织，不直接授予权限；直接分享的 relation 是定位记录主键的一部分，避免撤销一个角色误删其它角色。部门/公司继承通过成员关系解析，不按成员复制授权。资源操作仍重新鉴权。数据库租户 RLS 与授权判断同时生效，跨组织只在已授权的源资源读取范围切换。

## 管理员、组织层级与资源授权完整框架参考（2026-10-04，超出 MVP 部分延期）

本节保留此前完整框架讨论作为扩展参考，不代表本次全部实施。以文首最新 MVP 范围为准：平台管理后台、部门 lead 管理继承、owning_department_id、邀请接受、复杂移交均延期。以下“本期”“首期”“正式入口”等旧措辞描述当时讨论，不能覆盖最新范围；本次不新增这些模块或为其预建空表。成员关系、组织隔离、独立资源授权、真实操作者审计和撤权一致性仍是底层约束。

### 1. 目标与范围

同一个用户可加入多个公司，在不同公司、部门担任不同角色。平台维护人员管理平台，公司管理人员管理自己的公司，部门管理人员管理明确的部门范围；前端、API、CLI、Agent 使用同一套规则。采用现有 PostgreSQL、OpenFGA、RLS、审计与授权变更机制，不增加第二个权限引擎，不用角色数字大小判断权限。

本期定义平台、公司、部门和资源四类范围，保留有限内置角色。暂不做自定义角色编辑器、逐节点授权、逐文件独立分享、任意条件策略语言、跨公司部门树。审计、限时运维访问复用现有能力，不为本次设计重做审批系统。

### 2. 概念与归属：必须先固定的底层约束

- User 是全局账号；公司成员资格是该账号与某个 Organization 的关系。公司移除成员不等于删除全局账号。
- Organization 是租户隔离边界，区分 personal/business。个人空间继续存在，加入公司不会迁移个人 Workflow、Chat、文件或模型凭据。
- Department 是公司内部的管理范围，复用 Group(kind=department)。子部门只在同一公司下形成树，禁止环；用户可属于多个部门。Team 继续复用 Group(kind=team)，用于协作分享，首期不承担部门树的管理继承，不另造一个公司概念。
- 一份业务资源只有一个所属 Organization。分享不会改变归属；部门分享只是授权，不代表资源属于该部门。
- 公司资源可额外指定一个归属部门 owning_department_id（可为空，表示公司直属），与“分享给哪些部门”分开。它决定部门管理员的治理范围，不自动给部门全员内容访问权。
- created_by 仅表示创建者；资源负责人是可交接的业务管理关系。公司资源不因创建者离职变成无人管理的个人资源。
- 首期不实现个人资源和公司资源的一键跨租户迁移。若确需转移，后续单独设计版本、对象存储、执行身份及依赖迁移；不能只改 tenant_id。
- 操作始终记录真实操作者和资源所属组织。读取跨空间分享不冒充所有者，也不因挂载目录而获得所有者模型或 MCP 凭据。

### 3. 管理员角色与授权边界

| 身份 | 授予者 | 范围 | 核心能力 | 不能默认获得 |
| --- | --- | --- | --- | --- |
| 平台管理员 | 受控初始化/已有平台授权管理机制 | 平台 | 公司开通、停用、额度、系统状态；初始化公司所有者 | 任意 Chat 正文、个人文件、密钥、所有业务内容 |
| 公司所有者 owner | 公司创建/明确转移所有权 | 单公司 | 公司管理员任免、所有权转移、公司解散；其余公司管理能力 | 其他公司和成员个人空间的访问 |
| 公司管理员 admin | 本公司所有者 | 单公司 | 成员管理、部门管理、部门管理员任免、公司资源治理与审计 | 提升自己为 owner、任免 owner、其他公司的管理 |
| 部门管理员 lead | 公司管理员/所有者；上级部门管理员可委派给严格下级部门 | 指定部门及其子部门 | 部门成员分配、子部门维护、下级管理员委派、归属部门资源治理 | 修改上级或平级部门管理员、创建公司成员、全局账号管理 |
| 普通成员 member | 公司管理员加入/成员邀请接受 | 所在公司及自身成员关系 | 创建允许的资源，按显式授权操作资源 | 公司/部门治理权限 |

公司 owner 作为 admin 的特殊身份展示，不必新增复杂页面。允许多 owner，但始终至少有一个有效 owner。公司 admin 只管理普通成员及部门角色，不得借修改成员接口任免其他 admin/owner。部门 lead 只能从已有的有效公司成员中添加部门成员，不得根据外部邮箱创建公司成员。

部门管理员不必为了管理而变成该部门的普通业务成员。管理任命和成员关系分别记录；只有实际成员关系参与部门业务分享。若需要管理员同时使用部门资源，应明确添加成员关系或授予资源角色。界面须展示这一区别。

所有成员与角色变更首先验证操作者当前资格，并校验目标角色和目标范围；仅检查 manage_members 不够。禁止“拥有任意成员管理权就可以写任意 role”。不能移除最后一位有效 owner；该不变量须在事务锁下校验以防并发。

平台最初管理员通过受控部署/初始化入口配置；普通注册、创建公司和公司 owner 身份均不得产生平台管理员资格。本期公司开通由平台管理员完成；如果以后开放自助创建公司，应作为产品开通策略，不改变上述授权边界。现有自助创建接口需在实现前对齐该决策。

### 4. 组织治理与业务内容访问分别判定

组织角色回答“能管理哪些组织对象”；资源角色回答“能对这份资源做什么”。资源继续使用 viewer/editor/operator/manager：Workflow/Task/Deployment 的编辑与执行相互独立，Skill/Knowledge 使用 viewer/editor/manager，不能按角色排序推断权限。

公司和归属部门管理员可以：查看其治理范围内的资源标识、名称、类型、负责人和授权；交接负责人、管理授权、按规则停用或删除公司资源。默认不把组织管理员角色直接解释为全部资源正文、执行数据、Agent 对话和凭据读取权限。业务操作仍查资源动作授权。

必须明确治理权限的实际含义：能够管理授权的人，可以通过授予资源角色获得内容权限。这里提供的是默认不直接展示和操作的边界，不是保证管理员永远无法访问公司业务数据。修改授权/取得内容访问必须显式记录操作者、原因、前后权限。资源治理列表应提供管理入口，不能要求管理员先取得正文读取权限才能管理资源。

个人资源分享给公司或部门，仍属于个人：公司/部门管理员不获得该个人资源的治理权，也不能自行提升这次分享的级别。例如个人仅分享 viewer，公司管理员仍只能 viewer；不能因为管理分享对象而变成资源 manager。

Project、原始 Chat、Workflow 画布 Chat 继续不分享。Chat 快照分享沿用独立规则。沙盒不分享；模型/MCP 凭据不随管理员身份或业务资源分享自动开放。API Key 的管理不等于读取已有明文，沿用一次展示/轮换等现有机制。

平台运维需要诊断业务内容时，复用有范围、时效和审计的特权访问；不增加一个自动绕过所有资源检查的布尔值。主机/数据库运维本身的技术权限另受部署运维制度约束，不能宣称应用 RBAC 能阻止具有主机控制权的人读取底层数据。

### 5. 两条继承规则与部门移动

**管理继承向下**：公司管理员覆盖本公司部门；部门管理员覆盖其子树。不会向父部门、兄弟部门或其他公司扩散。继承来的管理资格不能在子部门通过删除本地授权解除，应到授权来源撤销。

**资源分享基于成员集合**：分享给部门时，明确提供“本部门成员”与“含子部门成员”，默认包含子部门；沿用 direct_member/member 两种关系，不复制一份用户 ACL。分享给公司表示有效公司 member/owner/admin，不包含 suspended/revoked 成员；现有 guest/auditor 不因角色名称自动加入全员业务分享。

例如研发部拥有 viewer 分享并勾选含子部门，则研发部与后端组成员可读。后端组另外获 operator，可读与可执行组合生效，仍不获得编辑。撤销后端组 operator 后保留研发部 viewer。个人直接授权同样与继承授权合并，不把“撤销某一路授权”等同于“完全无权”。

部门移动改变管理子树及含子部门分享的受众，应有变更预览：原父部门、新父部门、涉及的管理员/继承分享数量及移动后权限变化。确认后原子更新父关系和授权投影。首期仅公司管理员移动部门；不允许部门 lead 借移动把其他部门纳入自己的管理范围。有子部门、成员或归属资源的部门不能直接删除，应先转移/清理，避免静默丢失归属。

公司成员停用或退出应同时阻断其所有部门路径；恢复成员身份时须显式处理部门成员状态，不能恢复公司关系就悄悄重新激活已明确撤销的部门授权。业务资源来自其他公司或个人的独立直接分享，不因退出某一公司自动消失。

### 6. 成员加入与生命周期

正式产品采用“公司管理员发出邀请 → 用户在应用内接受 → 成为普通成员”。邮箱用于解析目标，内部使用不可变 user_id。首期仅邀请已注册账号，不发送邮件，站内邀请即可；不能用邮箱后缀自动认领公司。

直接按邮箱添加省一步，但会在用户不知情时改变其公司归属。先前草稿使用直接添加，尚未发布；正式入口确定为邀请接受流程。后台受控初始化可为指定 owner 建立初始成员资格；企业 SCIM 管理的成员仍由身份源维护，不能用原生邀请覆盖或重新绑定其身份。

邀请、成员资格分开记录：邀请 pending/accepted/cancelled/expired；成员 active/suspended/revoked。接受只能由目标账号完成，且重新检查邀请仍有效、公司仍可用、发起人仍有邀请权；默认 member，不接受客户端传入 owner/admin。重复邀请、重复接受须幂等，并保持 user_id+organization_id 唯一。拒绝/取消邀请不会创建成员资格。

公司管理员可暂停/移除本公司普通成员；owner/admin 的降权按第 3 节限制。部门 lead 只移除部门关系，无权停用公司成员或全局账号。退出公司不删除其个人资源；公司资源留在公司，由有效负责人接手。最后一个 owner 必须先完成所有权交接。

邀请方案已确定，本期采用站内通知，不接外发邮件、域名验证或完整企业目录同步改造。邀请默认 7 天过期；同公司对同一账号仅保留一份有效待接受邀请。取消或过期后可以重新发起。邀请不带管理员角色，接受后固定为普通成员；管理员任命使用独立管理操作。

### 7. 执行、凭据和退出后的行为

权限检查分为发起用户、资源归属、运行服务身份及依赖凭据四个维度。用户 Agent 始终沿用该用户权限，不因对话目标是共享资源而变成公司管理员或资源所有者。

分享现有 Task/Deployment 不改变其服务账号、计算资源及凭据绑定；点击查看或管理也不把运行身份切成接收者。新建实例/Workflow 交互运行按现有规则使用实际发起者可用资源。管理员变更、部门移动、负责人交接均不得静默更换模型 API 或复制密钥。

离职/停用流程必须列出绑定该人的运行资源和个人凭据依赖。受影响实例停止接收新的执行，待明确交接或停用；已有执行的纯计算可收尾，后续需要凭据/资源访问的动作仍做实时授权。安全紧急停用使用明确取消/停用能力，不把普通部门调整等同于杀死所有 worker。人工审批仍按指定审批人和当前权限校验，公司/部门管理员不自动代批。

Workflow 定义和 /run 可随既定分享规则开放，但不会因此开放其他人的数据库交互历史或 Chat。Task/Deployment 的实例历史、结果、Trace 按既定实例授权查看。撤权后新的详情/文件/结果请求应被拒绝；已经合法下载的副本不能远程收回，不能将残留副本视为新授权。

### 8. 存储与统一授权契约

复用现有结构，避免同一角色多处存储：

| 概念 | 权威存储建议 | 约束 |
| --- | --- | --- |
| 平台管理资格 | 现有平台特权资格表及其审计 | 不写入公司 membership，不在 User 增加全局万能 is_admin |
| 公司与成员 | organizations / org_memberships | 公司角色、有效状态、来源；一用户可多公司 |
| 部门树及成员 | groups / group_memberships | 同公司父子关系；部门角色与公司角色分离；原生/SCIM 来源受控 |
| 资源归属 | 现有 tenant_id + 可选 owning_department_id | 租户唯一；部门必须属于同租户；不得从分享目标推断 |
| 资源负责人、分享 | 现有资源关系及授权变更账本 | 用户/部门/公司主体、角色、成员范围、授予人；内部用 ID |
| 邀请 | 单独的轻量邀请记录 | 邀请人、目标 user_id、公司、状态、过期、接受时间；不复制用户密码/凭据 |
| 有效权限 | OpenFGA 关系计算 | 作为授权判定投影，不能代替业务成员/归属事实 |
| 审计 | 现有审计记录 | 真实操作者、范围、动作、目标、结果、前后差异、关联请求 |

数据库事务写业务事实和授权待办；提交后更新 OpenFGA。投影失败可幂等重试，撤销状态优先阻断访问。列表、详情、能力展示和 mutations 共用宿主机授权；不能仅靠列表筛选或前端隐藏保证安全。目录缓存只作发现，权限变更版本用于刷新，不作为永久授权凭证。

公共概念上每次判定提供 actor、action、resource、resource_organization、请求上下文；服务内部解析父资源、部门、有效成员关系和依赖范围。应用层不散落“role == admin 则放行”的判断。对成员管理还校验目标角色、来源、状态与委派范围，保证管理员不能自行提权。

### 9. 前端入口与说明

- 平台控制台：仅平台管理资格可见，公司开通/停用、额度及审计；默认不展示业务内容。
- 公司管理：公司所有者/管理员能看到成员、待处理邀请、部门树、资源治理、审计；普通成员看到自己的成员关系和可操作的邀请。
- 部门管理：明确标出管理范围和继承来源，只能选择本公司有效成员。继承管理员显示“来自上级部门”，跳转到来源处理，不提供无效的本地删除按钮。
- 业务资源详情继续显示“只读/可编辑/可执行/可管理”，与“公司管理员/部门管理员”身份标签分开；读权限开放的内容完整呈现，修改控件按能力禁用。
- 分享弹窗显示主体类型、角色、是否包含子部门和授权来源；撤销一项但仍存在其他来源时，明确提示仍有效的权限及其来源。
- 成员退出、部门移动、负责人交接使用小型影响确认窗口；不为普通读取和无害导航增加确认步骤。
- 个人/公司空间切换不改变全局账号，但改变可用权限范围；公司内直接分享仅在该公司空间生效，个人之间分享仅在个人空间生效。不能凭传入 owner ID 绕过空间边界。

### 10. 现有实现差异与分阶段落地

代码已具备 Organization owner/admin/member、Group lead/member、资源 ACL、平台限时特权访问、成员变更 outbox 和审计。但仍需逐项核对，不能因为模型存在就宣称方案完成：

1. 组织 manage_members 当前允许 owner/admin；成员更新接口还需要严格的目标角色委派规则，防止 admin 提升 owner。
2. group 的当前 lead 管理能力不自动继承子部门，需要独立定义管理子树，不能直接借用业务 member 关系。
3. 没有明确的资源 owning_department 管理归属；不能把分享到某个部门的个人资源当部门资产。
4. 公司邀请接受、初始 owner 和平台创建公司的流程尚未完成；未验证的邮箱直接添加草稿不能直接发布。
5. 公司治理权限与内容入口存在差异，需保证资源管理员能管理授权但不会凭组织身份误读私有 Chat/凭据。
6. 暂不改变本轮已部署的个人分享语义，避免把企业管理设计直接扩大为个人资源访问权。

实施顺序：以本节产品边界和动作矩阵为基线 → 固定数据约束/统一权限判定 → 公司成员邀请及管理员任免 → 部门管理继承及资源归属 → 前端治理入口 → 真实服务跨账号验收。每一步先写允许/拒绝用例，不以修改前端按钮代替底层授权。

### 11. 实机验收矩阵与完成门槛

两个给定账号轮换担任不同角色，配合两个独立测试公司、父子及平级部门、个人和公司资源。每次变更均通过真实管理入口/API，不能靠手工改数据库制造“已验收”的状态。

### 12. 已确定的产品选择

1. **公司成员加入**：采用站内邀请接受；不要默认未经用户接受直接把个人账号加入公司。
2. **公司业务资源治理**：owner/admin 和归属部门 lead 能管理其范围内公司资源的授权和负责人；个人资源的部门分享不受这一治理权覆盖。管理员可通过显式授权取得公司资源内容访问，该动作有审计。
3. **部门范围**：lead 管理子部门；资源分享默认含子部门，但可选择仅本部门，界面明确范围。

本节参考：Microsoft Entra 的角色与管理范围分离（https://learn.microsoft.com/en-us/entra/identity/role-based-access-control/administrative-units），GitLab 上级组权限继承（https://docs.gitlab.com/user/group/subgroups/），Keycloak 组织级委派管理（https://www.keycloak.org/2026/05/org-fgap）。以上产品并非规则完全一致，本节是结合 Flowork 私有对话、共享文件和运行身份要求提出的方案。

### 13. 设计边界复核与操作矩阵（设计补充，不改实现）

以下是代码静态核对得到的设计差异，尚未以真实公司角色执行攻击性操作，不应写成已经实机复现或修复的结论：

- update_organization_member 以 MANAGE_MEMBERS 为入口，UpdateOrganizationMemberBody 接受 owner/admin 等目标角色，OrganizationRepo.update_member 未接收操作者角色；前端 MemberAccessControls 也列出全部组织角色。因此必须补“操作者角色 × 目标原角色 × 目标新角色”的后端规则，不能只限制下拉框。
- update_member 检查有效 owner 数量后才更新，核对路径未见对公司/owner 集合加锁。若有两位 owner 同时退出，单独的数量检查不足以证明最后 owner 不变量；需同一公司串行化关键变更并在锁内重查。
- update_group 将修改名称和 parent_group_id 共用 UPDATE 权限。部门 lead 本来可改部门资料，不能据此允许移动部门；移动必须单独验证公司管理资格和源、目标归属，且展示继承权限影响。
- core.fga 的 lead 治理权限目前只覆盖直接任命的组；member 通过 descendant 扩展的是业务成员集合。不能把 member 的递归关系直接用于任命管理员，否则普通部门成员会混入治理授权。
- resource_access._resolve_group 目前仅接受 business 组织，并在资源当前组织内查找部门。这与设计稿提出的“个人资源分享给自己所在公司的部门”并不等价，后续必须分开解析资源所属组织与分享对象所属组织，不能为了找到部门而把个人资源切换成公司归属。

个人资源分享给公司/部门的边界：分享发起时，授权人必须同时有该资源 manage_access，并是目标公司的有效成员且有权选择该部门；目标公司不能从任意邮箱域名推断。解析令牌需同时绑定源资源与目标主体 ID/公司，防止换目标。分享保留个人归属，公司管理员无权升级该分享；资源管理者即使后来离开目标公司，也应能撤销自己资源上已经存在的这条分享，无需重新获得该公司的目录查询权限。退出公司不会自动撤销对外已发出的个人分享，退出页面应列出并允许本人明确撤销，避免隐式改变其他用户权限。本期设计包含此类分享，以满足个人、部门、公司的分享目标；它属于待实现、待实机验收能力，不能宣称当前已支持。

验收用例应直接对应上述每个单元格：允许操作检查实际业务结果、关系和审计；拒绝操作检查数据库/授权图不变；并发 owner 退出、部门移动与正在授予权限交错、邀请人降权后接受、退出公司后尝试旧组关系等必须单独覆盖。授权图暂时更新失败时，撤销请求应先在宿主机生效；旧允许缓存不能覆盖新拒绝事实。

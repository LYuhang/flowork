# Workflow 画布上下文对话设计

本文记录专业 Workflow 构建者在画布内通过 Agent 微调流程的交互与实现原则。用户可以针对全局、某个节点或某条连线直接发起对话，由 Agent 读取上下文、修改 Workflow 并提交新子版本。

状态：两个文档的实现已部署，16 类节点及多种上下文、异常、共享生命周期的实机验收已完成。最终逐项证据见文末；下方各日期小节保留阶段记录，早期“待验收”描述不代表最终状态。GitHub 推送在最终提交后核对。

## 目标与范围

保留手动编辑画布的方式，同时提供就地对话入口。例如，用户不知道如何编写 Code 节点代码，可直接在该节点右键发起对话，让 Agent 修改该节点，无需回主 Chat 重新解释 Workflow、版本及目标节点。

复用现有 Chat 的消息展示、编辑器、模型选择、附件、MCP 配置、消息持久化及 Agent 运行能力；复用 Workflow 的 CLI 修改、版本冲突保护和画布更新机制。避免另外维护一套功能不一致的聊天系统。

按本文实现画布对话；主页 Chat 继续使用共用链路，Task 与 Deployment 不新增画布对话入口。

## 入口与上下文

仅在画布当前可编辑时，右键菜单提供“🪄 在此处对话”。历史子版本、显式只读快照、无编辑权限以及执行期间禁止编辑的状态均不可触发。菜单与实际操作共用同一套可编辑状态判断，不能只在菜单层隐藏。

| 右键位置 | 小窗标题示例 | 会话目标 |
| --- | --- | --- |
| 空白画布 | `[v1.sv3] 全局 Workflow` | 当前 Workflow 全局 |
| 节点 | `[v1.sv3] 节点：数据清洗` | 节点 ID 及其相关上下文 |
| 普通连线 | `[v1.sv3] 连线：数据清洗 → 结果输出` | 连线标识、两端节点及端口 |

标题使用用户可读名称，内部以稳定的资源、节点及连线标识定位，不依赖名称或屏幕坐标。对于条件分支等情况，相同两端节点之间仍须能区分具体端口及连接。

每个大版本各自的最新子版本可编辑；对话只能修改启动时明确指定的大版本，不能跟随全局 HEAD 切换到其他大版本。

## 小窗布局

初始建议尺寸约 380 × 420 px，靠近右键位置展示，自动避开窗口边界，支持拖动及适度放大；具体尺寸可在实现时按实际组件布局微调。

小窗保持紧凑，但保留必要能力：

- 顶部：上下文标题、收起／关闭入口、历史会话入口。
- 中部：当前会话的消息历史，包括用户、Agent 及必要的工具执行状态。
- 底部：消息编辑框、模型选择、附件、MCP 选项、发送和执行中停止入口。
- 较少使用的配置收进工具菜单，复用主 Chat 的权限与选项行为。

消息区单独滚动，避免滚动画布；输入框与工具栏保持可见。弹窗不覆盖整个画布，用户仍可观察节点变化。

## 会话生命周期

1. 点击右键入口后先展示未发送的小窗，不立即创建持久会话或启动沙盒。
2. 没有发送消息时，点击外部空白区域即可关闭；再次打开时使用新的右键上下文。
3. 第一条消息发送前，若当前画布存在未保存修改，先保存。保存失败或出现版本冲突时，不启动对话执行，保留输入及附件供用户处理后重试。
4. 保存成功后，以返回的具体版本建立上下文，创建持久会话并确保 Workflow 沙盒可用，然后发送消息。
5. 已发送消息后，点击画布只收起小窗，保留对话及执行状态；通过历史入口选择原会话重新打开。收起不等于取消执行。
6. 再次选择“在此处对话”默认新建会话；历史入口允许重新打开当前 Workflow 的已有会话，避免强制新建或混淆不同上下文。

会话创建、首条消息提交和沙盒启动须防止重复点击造成重复会话或重复执行。启动失败应显示可操作的状态，重试复用已经创建的会话，不丢失用户输入。

桌面右键与触摸屏长按使用同一套上下文判定，均识别实际指向的节点、连线或空白，不能因缺少鼠标右键事件而将对话入口置灰。配对装饰线不作为可对话的普通连线。

画布下方工具栏依次展示缩放／适配等控制、添加节点、竖线分隔、新建全局对话、对话历史。移除独立的右下角悬浮入口。新建按钮以当前画布版本和全局 Workflow 上下文打开可输入的小窗；历史按钮恢复选中的原会话。在只读版本中隐藏新建入口，历史仍可查看，发送仍受只读规则约束。

右键／长按菜单另提供“引用为上下文”：仅在当前有打开、已就绪且可输入的画布对话框时启用。引用实际点击的节点、普通连线或全局 Workflow，加入当前编辑框的附件列表，不创建新会话。使用已有 `resource` 附件协议和 `workflow_elements` 选择器，固定 Workflow ID、具体版本及业务节点／连线端点。未保存的画布先保存，冲突或保存失败不新增引用；同版本同对象去重，支持移除，与文本和其他附件一并发送。后端继续通过现有附件解析器鉴权并生成可信源快照。右键打开菜单本身不收起活动对话框。

## Workflow 历史与继续对话

历史会话按 Workflow ID 归属和查询，覆盖该 Workflow 的所有大版本和子版本，不按当前画布版本割裂列表。用户权限仍沿用现有规则，不能因此读取其他用户的私有对话。内部 Project 只是复用后端的实现细节，前端历史入口不要求用户选择 Project。

每个会话在数据库中记录 Workflow ID、固定目标大版本、创建时具体子版本、全局／节点／连线目标及稳定 ID、上下文标题、创建时间和最后活动时间。每轮另存实际使用的具体版本、目标上下文及消息／执行时间；这些历史快照不可随当前画布更新而改写。

小窗顶部提供参考插件侧边栏的 History 按钮，复用现有历史菜单与查询机制，按最近活动倒序展示标题、版本、目标摘要和时间，并标出当前会话。列表支持分页；切换会话加载原有消息，而不是复制消息创建新会话。

历史列表中的初始版本来自会话创建时的绑定；继续对话后各轮实际使用的版本由对应输入快照记录，不用当前画布版本覆盖初始绑定。打开 History 时刷新列表，以便看到其他窗口新增的会话。未发送任何消息的草稿不列入历史。

历史会话支持 resume：继续使用原 chat_id、文件目录和原生会话关联，发送新的用户消息。它仍绑定原 Workflow、原目标大版本和选定节点／连线，不因当前画布位置或版本变化而更换目标。发送前刷新该大版本的最新子版本上下文并记录本轮版本；目标消失或权限失效时明确说明，不能悄悄替换目标。只读画布不启用发送；历史可读性与编辑权限分别校验。

前端加载和刷新沿用主对话框的持久消息、分页、活动执行发现及事件游标恢复机制。当前会话选择按用户与 Workflow 隔离持久化，刷新后先校验该会话仍属于当前 Workflow 且可访问，再加载历史并恢复已有执行流；不自动重发用户消息、创建新会话或重复启动 Agent。没有有效选择时显示历史或空状态。切换历史、收起小窗和刷新页面都不取消原有执行。

会话切换过程中按 chat_id 隔离请求、消息缓存和流式事件，防止慢响应把上一会话消息写进当前窗口。加载更早消息保留可见消息位置，沿用主页的滚动锚点逻辑。历史菜单、消息加载、空状态、错误重试和运行中恢复都应复用主 Chat 的机制，不能仅外观相似而实现另一套状态机。

## 后端复用方案

原则：前端是精简的画布 Chat，后端仍是现有 Chat。消息提交、流式回复、执行状态、停止、断线续接、历史分页、模型连接、MCP、Skill、附件解析、加密存储、Runtime 和沙盒管理均复用主页链路，不另建 Workflow 专用 Agent 执行器或消息表。

当前代码基础：

- `Chat.project_id` 必填，Project 管理 Runtime 连接、模型和 MCP 配置；每个 Chat 保留独立原生会话状态。
- `chat_workspace.py` 通过 Project 生成工作区 scope，当前工作目录已经是 `/chats/<chat_id>`。
- `ContextResolver` 已负责附件授权、持久引用和沙盒投影；跨工作区附件会复制到当前会话的 `contexts` 内容快照目录。
- 沙盒的 Chat 工作区已经持久化 `data`、`memory`、`logs`、`chats`，并支持重建时恢复文件。

推荐为每个“租户 + 用户 + Workflow”关联一个内部 Chat Project，在首次发送时按需创建并防止重复创建。同一用户在该 Workflow 的多个对话复用这个 Project；数据库中的会话可见性和模型配置沿用主页授权规则；沙盒文件按 Workflow 共享，不为内部 Project 增加独立文件隔离。内部 Project 不出现在主页普通 Project 列表，但使用同一套 Project 服务。它只是复用 Chat 数据和配置的关联容器，不据此额外创建独立对话沙盒；沙盒统一按已授权的 Workflow 运行资源解析。数据库历史查询仍按现有授权规则执行；目录共享不等于新增数据库历史读取权限。

新增信息集中在持久绑定与上下文生成两处：

| 层级 | 需要表达的信息 |
| --- | --- |
| 内部 Project 绑定 | 来源为 workflow、Workflow ID、用户与租户；数据库约束保证每个绑定唯一 |
| Chat 上下文 | Workflow ID、固定目标 major version、初始具体版本、全局／节点／连线类型和稳定目标 ID、端口 |
| 每轮执行快照 | 该轮实际读取的具体版本、目标是否存在、关联运行 ID 与版本、解析后的背景全文及 Runtime 输入 |

这些绑定由服务端校验后生成，不允许客户端直接指定宿主路径或任意工作区 scope。可以增加薄的“打开画布会话”入口完成权限检查、Project 查找和 Chat 创建；随后调用现有 Chat 消息、历史、停止等服务。来源标记不应借用现有 browser 或 sidepanel 的特殊行为，也不能只存在前端状态中。

模型默认采用用户当前有效的选择，之后由内部 Project 按现有机制保存；MCP、Skill 继续通过现有选择与授权流程解析，不自动复制不相关主页 Project 的配置。每次发消息仍重新校验 Workflow 编辑权限、目标版本可编辑性和 Chat 所有权；查看历史按现有读取权限校验。

鉴权直接复用主页 Agent 对话方案：登录、租户、模型连接、MCP、Skill、CLI、消息历史和执行控制均走现有检查，不新增画布专用角色、令牌体系或文件权限模型。画布会话只增加服务端校验的 Workflow 绑定，继续使用已有 Workflow 查看／编辑权限。prompt 中的上下文用于指导工作，不用于授予权限。

## Workflow 目录与持久化

对话文件统一归属于当前 Workflow 的隐藏 `chats` 区域，内部 Project 的文件引用映射到同一 Workflow VFS 和对象存储，不保存独立副本。新建 Workflow 初始化逻辑关联位置即可；首次发送再创建实际内部 Project 和会话目录，并获取 Workflow 共用沙盒；若先发生 run，则沙盒已经由 run 创建。已有 Workflow 按需补齐关联。

同一 Workflow 共用一套挂载，`/run` 和 `/chats` 对其中的 Agent 都可访问。`/chats/<chat_id>` 仅用于组织文件，不是访问隔离边界。主要依靠会话子目录和 prompt 说明区分当前工作范围，不增加每个 Chat／Project 的私人挂载、目录白名单或只读限制。

| 路径 | 用途与规则 |
| --- | --- |
| `/chats/<chat_id>/` | 当前会话的工作目录，直接复用主页现有规则 |
| `/chats/<chat_id>/attachments/<attachment_id>/<filename>` | 本会话上传附件的推荐目标；独立附件 ID 避免同名覆盖 |
| `/chats/<chat_id>/contexts/<digest>/<filename>` | 复用现有跨资源附件快照路径，保留内容身份 |
| `/data` | 同一 Workflow 内各会话可共享的资料与产物 |
| `/memory` | 当前 Workflow 的持久工作记忆，不与其他 Workflow 混用 |
| `/logs` | Agent 工作文件和工具产物；不替代数据库消息与执行事件 |
| `/run` | 当前 Workflow 的运行产物目录，沿用现有读写和清理逻辑，不新增只读限制 |

`/run` 对应共用沙盒中当前 Workflow 的运行产物，不把主页 Chat 自己的 run 目录误称为 Workflow 上次运行。接受用户重新执行时该目录可能清空或变化；本阶段不为 Agent 读取新增文件快照、目录锁或一致性机制。上下文中已有的运行 ID 与版本用于说明来源，不保证后续文件读取仍对应同一份内容。用户显式添加附件时，继续沿用现有 ContextResolver 行为。

附件继续使用现有上传、大小限制、扫描、文件引用、预览、下载、授权和热沙盒文件同步机制，只改变服务端计算的目标 Project 与路径。未发送的小窗选中文件后，先保留前端待上传状态；首次发送时创建会话再上传。上传失败不启动 Agent，保留已经创建的会话及成功上传的引用供重试，避免为“选了附件但关闭小窗”创建长期会话。

数据库保存会话、展示消息、双份输入记录与历史索引；文件内容依赖挂载的对象存储持久化，VFS 沿用现有文件索引与授权机制。沙盒只提供运行资源，本地文件是对象存储的挂载、缓存或投影，不能作为持久文件的唯一副本。聊天内容不以目录里的 JSON 文件作为另一份权威记录。历史入口通过数据库关联查找，不能靠扫描文件夹。

文件的读取、写入与恢复沿用主页已有的对象存储挂载／同步机制。采用本地投影时，必须保证写回成功才将文件标为已持久化；正常回收前完成待写回内容，写回失败不能伪装为成功或直接丢弃唯一副本。沙盒重建后重新挂载或恢复同一持久命名空间，不能初始化空目录并覆盖已有文件。异常退出时不得承诺恢复尚未成功持久化的内容。

`chats` 和内部 Project 文件不显示在 Workflow Explorer。清理或重建 Workflow 的 `run` 不得删除聊天文件；关闭小窗不删除历史。删除 Workflow 时沿用既有资源删除与授权流程处理关联会话，不新增独立的定期聊天清理策略。

## 共用沙盒与空闲回收

同一 Workflow 的画布运行和上下文对话使用同一个沙盒。复用主页的 SandboxManager、Runtime adapter、挂载和持久化实现，在 Workflow 沙盒内建立 Agent Runtime worker；Workflow 执行 worker 和 Agent Runtime worker 分别处理各自任务，每个 Chat 在 `/chats/<chat_id>` 中建立原生会话。内部 Project 与主页 Project scope 的映射需要适配，不沿用“每个内部 Project 再启动一个沙盒”的方案。

无论开始对话还是开始 run，都通过同一入口获取沙盒：不存在则创建，存在则复用。创建后保持沙盒，不因某次执行结束立即关闭。对话与 run 同时首次触发时也只能创建一个实例。

| 活动状态 | 沙盒与 TTL 行为 |
| --- | --- |
| 对话或 Workflow 执行仍在进行 | 保持沙盒，不进行空闲倒计时；工具调用和等待人工审批均属于活动 |
| 对话和 Workflow 执行均无活动 | 从最后一个活动结束时开始完整的空闲 TTL 倒计时 |
| 倒计时内收到新对话或 run | 取消倒计时，复用沙盒；等所有活动结束后重新计算完整 TTL |
| 空闲 TTL 到期 | 再次确认没有新活动并完成文件持久化，再释放沙盒运行资源 |
| 回收后发生新活动 | 重建沙盒，挂载或恢复相同对象存储文件，并读取数据库中的对话历史 |

活动判断应覆盖已接受且排队等待执行的请求，避免等待 worker 期间误回收。已完成的聊天记录、单纯打开画布、查看历史及前端连接保活不算执行活动。多个 Chat 和 run 使用汇总活动状态，不能由某个任务结束直接把整个沙盒标为空闲；TTL 到期检查和新任务进入之间必须避免竞态。

停止 Chat 只停止对应 Agent turn，停止 Workflow 只停止对应 Workflow 执行。worker 超时或取消不能直接关闭整个沙盒；最后一个活动结束后统一进入空闲倒计时。清空 `/run` 仅按既有 Workflow 执行规则作用于对应运行文件，不清空 `/chats` 或整个挂载根目录，也不能取消对话。

沙盒正常释放只回收进程和临时运行资源，不删除对象存储文件或数据库中的对话记录。沙盒重建后的文件与消息恢复不等于恢复原来正在执行的 worker；意外重启后的执行失败处理沿用既有规则，原生 Chat 会话缺失时沿用主页恢复机制。

按用户最新确认采用软隔离：Workflow 执行和 Agent 对话使用同一沙盒资源与共享文件，只是两个不同的 worker 进程。prompt 说明当前会话目录、Workflow 版本和修改范围，默认在当前会话目录组织文件，避免误改其他会话。不同 Workflow／租户的资源、数据库历史查询和凭据仍沿用现有鉴权机制；不新增沙盒内文件硬隔离。

`/run` 属于 Workflow 执行产物，复用同一文件来源和现有持久化路径，不新增一套 Chat 专用运行目录写回。模型、MCP、技能与文件授权沿用主页机制，不通过背景文本授予权限。

## 本阶段明确的简化取舍

- Workflow run 沿用启动时已固定的版本。Agent 经 CLI 提交新版本不切换正在执行的 Workflow 定义；本需求不另外设计一套版本冻结机制。实现时核对既有行为即可。
- 接受对话读取 `/run` 与用户重新执行同时发生时文件变化的低概率情况，不新增运行文件快照或读写协调机制。
- 不为画布 Agent 新增沙盒内目录写入白名单或只读挂载约束，沿用主页已有权限与文件操作能力。Workflow 结构和节点配置的修改仍通过现有 CLI 完成。既有租户、用户及资源授权保持有效。
- Workflow worker 与 Agent Runtime worker 分开处理任务、停止和取消。本阶段不新增第二个 worker 的 CPU、内存或并发配额；后续有实际资源争用时再约束 Agent worker。不同 worker 仍共享沙盒总资源，不将其描述为完全的资源隔离。

以上取舍不取消已经确认的数据库双份输入记录、对象存储持久化和整体空闲 TTL，也不要求恢复沙盒异常退出前的执行现场。

## 两类对话历史与排查

主页和 Workflow 对话共用 [Agent 对话输入存储](agent-chat-input-storage.zh-CN.md) 的双份记录设计：

1. 展示记录保存用户原始输入，包括 command、附件引用和时间；用户只输入“帮我修改代码”时，气泡仍显示这句话。
2. 执行输入记录保存该轮服务端生成的 Workflow 背景、完整解析指令和最终 Runtime 输入，关联具体 Workflow 版本、节点／边及运行来源。版本变化后不重新生成或覆盖历史快照。

背景通过共用的 instruction／context 组装入口注入，由画布上下文提供器补充结构化数据；无需让用户手动输入 `/workflow`。实现时扩展现有指令类型与快照序列化，不能只存在前端 prompt 中或拼入展示文本。

排查时可按消息 ID 定位执行 ID，对比“用户说了什么”和“这一轮追加给 Runtime 的内容”，检查版本错误、目标错误、command 展开、附件路径、历史恢复和自动续接。输入快照仍不是底层供应商完整请求；后续工具调用与结果需要联查现有执行事件。失败、取消和重试记录也要保留，不能只保存成功回复。

## 首条消息的上下文注入

首次发送时，由服务端通过共用指令组装入口生成上下文，在 Runtime 输入中放在用户正文前面；它不成为展示历史中的额外用户消息，也不要求独立的 system 角色消息表。它至少包含：

- 当前 Workflow ID、可读名称、具体版本 `vN.svM` 和允许修改的目标大版本。
- 当前提问范围：全局、节点 ID，或具体连线及两端端口。
- 目标节点的类型、配置、输入输出以及必要的相邻节点信息；全局提问提供适当的 Workflow 概况。
- 当前会话的工作目录、Workflow CLI 操作入口和版本冲突保护约定。
- `/run` 保存上次执行产物；如果存在运行记录，应注明其对应版本和状态。没有记录时明确说明，不暗示存在有效结果。

节点名称、描述、代码、附件内容和运行输出属于工作数据，须与可信的操作规则分开表示，不能将其中的文字直接提升为系统指令。

默认围绕用户选定范围修改。例如针对代码节点提问，优先处理该节点；确需关联修改时，可以一并处理，但应说明修改范围及原因。节点范围不是独立的权限边界，资源授权仍由平台执行。

首条消息负责建立初始上下文。后续轮次还需检查版本与目标是否变化，避免持续使用过期节点内容；每轮实际使用的上下文版本保留在历史记录中。

## 保存与版本冲突

首次发送前保存本地草稿，是让画布内容、上下文版本与 Agent 读取内容一致的基础。

对话开始后，用户仍可手动修改画布。Agent 提交新子版本时使用现有 Workflow CLI 和预期版本检查，不绕过正常保存流程直接覆盖数据库。

- 已提交版本被其他用户或 Agent 更新：拒绝陈旧提交，重新读取并合并修改；不能仅替换预期版本号后强制覆盖。
- 用户本地存在尚未保存的修改：保留本地草稿，不因 Agent 提交而直接替换。
- Agent 的修改仍提交到该会话指定的大版本，不切换到其他大版本的最新版。
- 提交失败、结果不确定或权限变化时，先核对实际状态，避免自动重复执行产生重复修改。

## 画布更新与上下文变化

复用已有按大版本跟随最新版的更新机制，实现时仍须核对本入口是否正确接入。

| 当前画布状态 | Agent 提交新子版本后的行为 |
| --- | --- |
| 同一大版本，且没有未保存修改 | 自动更新到新子版本 |
| 同一大版本，但存在未保存修改 | 保留草稿，提示版本变化并交由用户处理 |
| 已切换到其他 Workflow 或其他大版本 | 不把会话修改强行应用到当前画布 |
| 历史或显式只读快照 | 保持固定快照，不升级成可编辑页 |

更新时尽量保留视口、缩放和仍存在的节点选择。会话标题展示其上下文最新确认的版本，历史消息仍保留各轮使用的版本；用户切换画布不能偷偷改变已有会话的修改目标。

如果目标节点或连线被删除，应明确提示目标已不存在，暂停依赖该目标的修改，不能根据相近名称悄悄换成另一个节点或连接。

## 真实服务验收

实现后必须部署到真实服务验收，不能只以组件测试或静态代码检查作为完成依据。

1. 空白、节点、连线三种右键入口的标题和目标准确；不同端口或分支不混淆。
2. 旧子版本、显式只读视图、无编辑权限及执行冻结状态无法触发新对话。
3. 未发送时点击外部关闭，不创建持久会话或启动沙盒；已发送后收起、重开，消息与执行状态保留。
4. 模型选择、附件、MCP、发送和停止沿用现有 Chat 行为；停止对话不影响无关执行。
5. 首次发送前保存草稿，使用保存返回的版本；保存失败、冲突和重复点击不产生错误会话或重复执行。
6. 在 Code 节点发起自然语言修改，Agent 实际提交新子版本，画布自动更新；修改属于正确的大版本，范围符合用户要求。
7. 手动修改与 Agent 修改并发时，未保存内容不丢失，陈旧版本不能覆盖新版本。
8. `run` 清理不影响聊天历史；`chats` 不出现在 Explorer；重新打开会话可恢复持久消息。
9. 上次执行属于其他版本时，上下文明确区分；没有运行记录时不捏造结果。
10. 切换 Workflow、大版本，或删除目标节点／连线后，不误改其他对象；租户和 Workflow 不串用，数据库会话查询沿用现有权限。

11. 对比同一轮原始消息与展开快照，确认 Workflow 版本、目标、附件和运行来源准确；后续版本变化不改写旧快照。
12. 主页与画布的发送、重试、停止、历史恢复、MCP、Skill、附件预览走相同后端链路；空回复重试和自动续接均可回溯输入。
13. 同一 Workflow 的 Agent 能访问共享 `/run` 和 `/chats`；不同会话按 `/chats/<chat_id>` 和 prompt 区分工作范围，没有额外目录访问限制。不同 Workflow 不混用工作区；数据库历史与模型凭据沿用现有授权。
14. 附件上传失败可重试，关闭未发送小窗不启动沙盒；同名附件不覆盖，热沙盒可立即读取成功上传的文件。
15. 先对话后 run、先 run 后对话以及同时首次触发，均复用同一个 Workflow 沙盒；停止某个 worker 和清理 run 不影响其他活动或聊天文件。
16. 有对话、run、排队请求或人工审批等待时不启动空闲回收；全部活动结束后才计 TTL，新活动取消倒计时，最后一个活动结束后重新计时。
17. TTL 到期与新请求并发时不会误回收；正常释放后对象存储文件与数据库历史仍存在，重建后能读取相同文件。验证写回失败不被当成持久化成功，恢复过程不覆盖已有文件。

18. 同一 Workflow 的不同大版本和节点／连线会话在 History 中可找到，标题、版本、上下文、创建和活动时间可核对；其他 Workflow 的会话不混入。
19. 切换历史会话后以原 chat_id 继续对话，关联版本与目标正确；切换期间旧流不串入新会话，原执行不被取消。
20. 空闲、执行中和断线后刷新页面，均按主页机制恢复当前会话、持久历史及活动流，不重复发送或执行；更早消息加载不跳动。失效会话引用和权限变化有明确状态。

### 2026-10-03 共享 worker 停止与文件保留补验

### 2026-10-03 TTL 排队与边界实机补验

为避免再次等待全局 30 分钟 TTL，使用公开 API 创建独立 QA Workflow，在真实服务器上直接运行已部署的 SandboxManager、gVisor 执行器和既有持久存储。仅独立测试进程的 manager 使用 6 秒 TTL；没有修改线上沙盒服务的配置，也没有替换时钟、执行器或文件存储。这是已部署组件的原生集成验收，区别于通过页面等待默认 TTL 的观察。

- 两个同沙盒代码请求分别运行 10 秒和 2 秒，第二个等待第一个释放执行锁。22 次实际观察中出现两个活动请求；整个运行和排队阶段，真实 sweep 均未回收沙盒。

### 发送反馈及并发

实机基线：同一 Workflow 的全局、节点、边上下文各开一个独立浏览器页面，使用 Terra 同时发送两轮只读请求，共 6 次。全部完成，未出现跨对话标记或上下文串线。首次消息气泡出现需要 6.2–9.4 秒，后续发送约 3.9 秒；主要等待发生在新对话创建和草稿保存请求，不是等待模型首字。

发送时首先在本地对话列表显示用户消息及“正在准备消息”。这不是服务端已接受或模型正在执行的状态。原始草稿暂时保留，准备成功后交给正常消息流，失败则恢复显示编辑框原文与附件。准备状态按 chat_id 独立存储；准备期间禁用编辑框和新增附件，避免显示内容与待发送快照不一致。复用既有草稿同步、版本冲突和服务器接收协议，本次没有移除这些保护。

创建对话只发生在新对话；画布只有未保存修改时才提交；文件只有新附件需要上传；MCP 只有首次自定义选择时保存。发送前草稿同步仍存在，可以另行优化为发送快照与草稿版本的统一提交，但必须处理已发出草稿请求晚于消息到达和另一窗口的新草稿，不能直接删除 await 后将旧草稿重新写回。

### 模型节点验收注意事项

SubAgent 曾在一次真实执行中以普通文本结束，未调用必需的 set_output；随后原图重跑成功。该首次失败计入验收记录，不能因重试成功而忽略。按用户确认的简化方案，仅强化 system prompt，明确必须调用 set_output 提交全部声明字段，普通文本或代码块不算完成；不追加用户提醒、不另起纠正对话。参数通过校验后立即结束节点，不继续调用模型。同一条模型响应中附带的文字只保留在 trace，不参与节点输出；参数校验失败时仍允许在原有迭代额度内修正工具参数。未提交合法输出继续失败。此前试验性的额外纠正逻辑已撤回。

修复后的同类三页面、两轮并发共 6 次请求均成功，自己的标记均正确且未出现其他对话的标记。点击至消息气泡可见的自动化测量为 0.79–1.43 秒（包含浏览器自动化点击与渲染成本），修复前为 3.89–9.38 秒；模型完整处理耗时没有作为此次 UI 优化的收益。

真实浏览器还对新会话创建请求注入延迟与 503：点击至准备消息 DOM 出现为 49 毫秒；失败后正文及节点引用均恢复，消息接口请求数为 0，列表无残留气泡。该测试仅注入准备接口失败，不代表模型服务故障覆盖。


CLI 结果轮询复测发现一个独立问题：授权后端暂时不可用时，Host 原先将已受理的执行停止并移出注册表，而 Gateway 又会重试同一游标，因而返回 result_unknown。现在暂时不可用只拒绝本次结果读取，保留执行和游标供已有的有限重试；不续租，持续不可用仍会触发既有租约回收，实际权限撤销仍停止执行。直接异常和由 PermissionError 包装的不可用异常均覆盖，连同 SubAgent 共 40 项后端测试通过。

原第 12 轮因上述问题取消，未算作人工通过验收。修复部署后，第 15 轮从真实 trace 页面点击通过，同一次执行成功得到 RESULT: 10、doubles: []、review_status: approved，覆盖空循环及人工通过路径。此轮已使用最终的 prompt-only SubAgent 实现。授权服务日志另有数据库 I/O timeout；20 对相同只读请求比较未复现差异，没有据此更改 OpenFGA 配置，也不宣称底层偶发问题已彻底消失。

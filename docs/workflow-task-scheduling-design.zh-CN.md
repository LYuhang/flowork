# Workflow 与 Task 定时执行设计

本文记录 Workflow 页定时执行入口、一次性固定时间任务及周期任务允许重叠执行的设计，供实现与验收使用。实现与真实服务验收已完成，证据范围记录在文末及验收记录中。

核心要求：Workflow 页默认使用用户当前看到的画布版本；两个页面共用任务创建和执行机制；固定时间任务只触发一次；周期任务不能因为上一次仍在运行而跳过本次触发。

实现统一采用最新规则，不增加旧调度行为的兼容开关或双轨逻辑。已有任务通过数据库迁移统一切换为允许重叠执行；历史执行记录保留。删除过时的服务端分支、界面提示、CLI 和 Agent 说明，不将旧行为继续作为可选策略暴露。

## 两个入口共用任务逻辑

Workflow 页面增加定时执行入口，与单次执行、批量执行并列，打开右侧 Inspector 的定时执行页签。Task 页面继续提供任务创建入口。

两处创建的是同一种 Task 资源，必须共用表单核心、输入转换、参数校验、请求构造、创建 API、服务端创建服务、权限检查和调度执行链路。不能为 Workflow 页面新增一套独立调度器或任务执行接口。

| 项目 | Workflow 页面 | Task 页面 |
| --- | --- | --- |
| Workflow 来源 | 自动带入当前画布的 Workflow | 用户选择 Workflow |
| 版本来源 | 默认当前实际展示的确切版本 | 用户选择确切版本 |
| 未保存内容 | 创建前先保存当前草稿，成功后绑定返回版本 | 使用已保存版本 |
| 时间配置、时区、输入校验、挂载、通知 | 共用组件与规则 | 共用组件与规则 |
| 创建后的任务与执行 | 进入统一 Task 管理与运行机制 | 进入统一 Task 管理与运行机制 |

相同版本、输入和调度配置从两处提交，除任务名称、创建时间、生成 ID 等差异外，应得到相同的有效配置、权限判断、触发行为、状态、日志和结果。该要求也适用于已有批量任务的共同配置和执行语义；画布单次调试仍保留现有交互，不改造成后台 Task。

提取或复用现有 ScheduledRunCreatePanel 的公共部分，不复制两份逐渐分叉的表单逻辑。CLI、API 模型、帮助说明和 Agent 使用说明必须同步核对新增调度类型与并发语义，避免前端支持而其他入口仍按旧规则处理。

## 版本与创建流程

Workflow 来源必须是用户当前看到的画布版本，而非全局最新版本或某大版本的最新版本。明确显示名称及具体版本，任务创建后固定该版本，不跟随后续编辑。

有未保存修改时，按钮显示“保存并创建定时任务”，先完成保存，再使用保存返回的确切版本提交。保存失败或冲突则停止创建并保留表单。保存成功但创建失败时，保留已保存版本和表单，重试不能无故再次生成版本。

面板打开期间切换画布版本时，明确更新目标并重新校验输入；不能把旧版本字段静默提交给新版本。自动版本更新同样遵守现有未保存修改保护。

历史版本是否允许创建任务按实际执行权限判断，不能仅因为不可编辑就误判为不能使用该版本。Trace 等纯查看页面不因此自动增加创建入口。

任务名称允许修改，默认由 Workflow 名称生成。输入根据目标版本 Start 节点生成，可首次从画布单次执行表单带入，之后独立编辑。说明每次执行复用固定输入，动态数据由 Workflow 内部获取。

## Cadence 分类

两个页面使用相同选项与顺序：

| 英文选项 | 中文说明 | 行为 |
| --- | --- | --- |
| Fixed time | 固定时间，仅执行一次 | 指定年月日时分秒，只产生一次计划触发 |
| Specific time | 周期时间 | 按每小时、每天、每周、每月或自定义 Cron 触发 |
| Fixed interval | 固定间隔 | 按指定间隔持续触发 |

英文说明也必须区分 one-time 与 recurring，避免前两项名称相近产生歧义。界面顺序不等于用户已经选定执行时间，不能隐式提交默认的未来时间。

## 一次性固定时间

采用日历与时间组合选择器：日历选择年月日，时间区选择小时、分钟、秒，使用 24 小时制，也允许键盘输入完整日期时间。支持快速切换年月，点击确定后确认选择。

展示格式为 YYYY-MM-DD HH:mm:ss，并单独明确显示 IANA 时区，例如 Asia/Shanghai。下方用自然语言显示“将在某年某月某日某时某分某秒执行一次”。

时间转换和校验使用公共逻辑，服务端为最终依据：

- 保存对应 UTC 时间点，同时保留用于展示的时区。
- 提交时必须仍在未来，已过期则提示重新选择。
- 夏令时导致不存在或重复的本地时间时，必须明确处理并让用户确认实际时间点，不能静默偏移。
- 一次性模式隐藏重复周期、开始时间和结束时间，避免重复配置。
- 后端采用明确的一次性调度类型及目标时间字段，不用 Cron 或极长 interval 模拟一次性执行；具体字段名在实现时统一到 API 与 CLI 契约。

任务在指定时间产生一个执行记录，随后不再生成下一次执行。重复投递或调度器并发领取同一触发时，应依靠持久化的唯一触发标识避免重复创建执行；这不等于保证外部业务副作用恰好发生一次。

已触发后不能通过简单恢复开关再次触发同一个计划。执行结束后保留任务、结果和日志，成功或失败按实际情况显示，失败不自动重跑。下一次执行时间显示为空，而不是伪装成仍有待执行计划。

未触发时暂停任务会阻止触发；若恢复时目标时间已过，要求重新选择未来时间。暂停期间过去的计划不应在恢复时悄悄执行。服务异常导致未暂停的一次性任务错过时间的恢复策略，需要在实现设计中明确区分，不能套用周期任务的跳过历史时间计算而将唯一一次执行静默丢弃。

## 周期任务允许重叠执行

移除“前一次仍活跃则跳过本次”的调度行为，不仅是删除前端提示。每个正常计划触发都创建独立 execution，不等待前一次结束，也不取消或覆盖前一次。

例如每分钟触发一次、每次执行三分钟，09:00、09:01、09:02 都应产生独立执行并允许同时运行。前次等待人工审批也不阻止后续计划触发。

Fixed interval 按计划时间推进，不按前次完成时间计算间隔，避免任务耗时改变执行频率。同一计划时间仍需去重，不能因允许并发而重复触发。

资源正常时到点启动；容量不足时保留该次执行并明确排队，不因前次活跃而标记 skipped。区分计划触发时间、实际开始时间及排队延迟，不能承诺无资源情况下仍能精确按秒开始。排队记录可在 history 查看，执行日志与画布详情在实际开始执行后提供。

提示文字更新为：“每个计划时间都会触发独立执行。即使上一次尚未完成，新执行也会照常启动。资源不足时可能排队。” 同步修改中英文界面、帮助文档、CLI 输出及调度策略字段，不能留下行为仍为 skip 的入口。

服务停机后的历史周期是否补发属于独立的 catchup 策略，不能与前次执行未结束时的重叠策略混为一谈。本次确认的是取消因前次活跃而跳过；停机历史补发不在本文中默认扩展。

## 多次执行的隔离与状态

每次执行具有独立 execution ID、版本与输入快照、状态、日志、结果、审批上下文及运行目录。某次取消、超时、失败或清理资源，不能影响其他执行。

任务层区分调度状态与执行汇总，例如“计划已启用，运行中 3 次，排队 1 次”。某个执行完成时，不得把仍有其他执行运行的任务更新为全部完成。并发乱序结束时，最近执行等摘要应有明确排序依据，不能只靠最后一次写入覆盖。

任务层只保留计划配置、执行数量与状态摘要，不复制某次 execution 的业务结果或错误。业务结果、错误、Logs 和 Trace 均以 execution ID 为查询和操作边界。日志允许共用物理表，但执行筛选必须在对外分页、游标和条数限制之前完成，不能先截取任务日志再过滤，造成其他并发执行挤掉目标执行的日志。实时任务事件流可用于刷新概览，不能将其中某次执行的错误或结果写回任务概览。

排队阶段只生成 history 中的执行记录，手动触发与自动触发一致；尚未开始就取消的执行也不生成运行日志或 Trace。

日志、执行详情、审批和取消操作必须定位具体 execution。暂停计划只阻止未来触发，不自动取消已经创建的排队或运行执行。已派发的一次性任务同样通过取消具体 execution 处理。

临时文件和内部运行资源需要隔离；用户主动配置的共享挂载或外部系统不因此自动获得隔离，不能依赖过去的单执行限制保护它们。实现时需检查结果文件命名及清理范围，避免并发互相覆盖。

## 创建成功后的交互

按钮默认“创建并启用”，关闭启用开关时为“创建任务”；有草稿时相应体现先保存。提交期间禁用重复点击，并按公共创建机制防止重复提交。

Workflow 页面创建后留在画布，显示任务名称、固定版本、时间摘要和“查看任务”“再建一个”。不额外立即执行一次。“查看任务”进入统一 Task 详情页，由该页管理计划和执行记录。

周期配置可显示接下来三次预计触发时间，一次性任务只显示唯一目标时间；预览必须与服务端计算规则一致。Task 与 Workflow 两处使用相同成功提示、校验信息和错误语义。

## 实机验收要求

功能必须部署到真实服务验收。单元测试、接口模拟或仅检查创建成功均不能替代实际触发与执行验证。

- 从 Workflow 与 Task 两个入口分别创建三类调度，核对有效配置、实际触发、日志和结果一致。
- 验证当前画布版本、历史版本、未保存修改、保存失败与冲突、创建失败重试，以及打开面板后切换版本。
- 验证年月日时分秒选择、键盘输入、时区转换、过去时间拒绝及夏令时边界。
- 验证一次性任务按指定时间触发且只创建一次计划执行，结束后无 next run，成功与失败记录均保留，暂停恢复不会隐式重跑过期计划。
- 验证周期任务前次运行时间超过周期、前次等待审批时，后续仍按时产生独立执行；Fixed interval 不随完成时间漂移。
- 验证资源不足时排队可见，计划时间与实际开始时间可区分，无静默跳过，无重复领取。
- 验证并发成功、失败、取消、超时和乱序结束时，任务汇总正确，各执行日志、结果、审批和资源清理互不干扰。
- 验证暂停计划不影响已派发执行，单次取消不误取消其他执行。
- 验证 API、CLI、Agent 说明及两处前端文案与新行为一致，并回归已有批量任务创建逻辑。

## 实现及验收进度（2026-10-03）

实现使用 `schedule_type=once`、带时区的 `run_at`；迁移 157 将现有任务统一切换为允许重叠执行。Workflow 与 Task 使用同一个 `ScheduledRunCreatePanel` 和创建 API；没有旧调度策略开关。

已部署到 `https://flowork.top`，当前已取得的实机证据：

- Workflow 与 Task 两个入口各创建 Fixed time、Specific time、Fixed interval，六个任务均实际触发，结果和固定版本一致。
- 一次性成功及失败均保留执行结果/错误与 Trace，没有 next run，不重复触发；过期或已触发计划不能通过恢复开关重跑；暂停期间到期的任务不执行。
- 历史画布绑定该历史版本；草稿先保存，保存后创建失败保留表单，重试不重复保存；真实版本冲突返回 409，未创建任务且保留输入。
- 临时将测试队列并发设为 2，观察到两个独立人工审批同时等待、第三个排队。暂停不取消已派发执行，乱序批准、驳回、取消相互独立，固定间隔仍以计划时间推进；测试后恢复原队列并发 1。
- 排队记录没有 Trace；已运行执行的结果、错误及分页日志均按 execution 查询，任务概览不复制执行结果或错误。
- UTC/+08:00 转换保留秒，服务端拒绝无时区时间；原有批量任务实际执行与日志回归通过。

自动化验证已通过后端相关用例 130 项、人工审批真实 RPC/数据库用例 6 项、前端相关用例 38 项，TypeScript 检查、生产构建和部署路径检查通过。人工审批 RPC 测试使用隔离数据库及服务账号可访问的测试源码，不访问生产数据。

最后一轮实机检查已通过：切换画布版本后清空旧输入并提示、日历年月日和 24 小时时分秒、DST 不存在/重复时间的明确拒绝、未启动即取消不产生日志或 Trace、跨时区创建摘要与配置展示。普通 7 秒代码执行在 4 秒计划间隔下保留后续排队执行；并发失败及审批超时不影响另一条执行，较早执行晚完成不覆盖较新执行的失败摘要。队列已恢复原并发上限 1，验收结束时无活跃测试任务。

## 任务通知与跨版本追溯（2026-10-03）

- Workflow 工具栏保留一个执行入口，批量和定时执行放在执行 Inspector 中。
- 批量和定时任务共用通知配置：成功时通知、失败时通知，默认均不勾选。任意一项勾选后显示单个收件用户 Email 输入框，要求合法邮箱；配置随任务保存。
- 通知发送函数仅保留 `pass`，不发送邮件、不创建通知队列、不标记已发送。定时执行命中策略时记录 `skipped / delivery_not_implemented`。取消或中断不作为成功或失败通知。
- CLI 创建两类任务时均可使用 `--notify succeeded,failed --notify-email user@example.com`；不指定时关闭通知。定时任务更新通知配置时也使用这组参数。
- 两个 Inspector 使用相同的关联任务列表，分别展示该 Workflow 所有版本的批量任务、定时任务。列表支持分页、复制完整任务 ID、直接跳转任务详情，并显示实际绑定的 `vN.svM`，不使用当前画布版本替代。
- 列表中的任务中心链接携带 Workflow ID 和任务类型。Task 页面支持 Workflow 筛选；切换任务类型保留筛选，分页和状态统计也使用该 Workflow 范围。
- Workflow 批量提交也必须固定具体版本：未修改时取当前画布 `baseVersion`，有修改时取保存操作返回的版本；不能只发送主版本号并在后台重新解析最新版。

## Workflow 部署入口与版本编辑规则（2026-10-03）

- 工具栏在执行旁提供部署按钮，按 Workflow 的 `deploy` 权限控制；打开 Inspector 的 Deploy 页签。
- 部署页签复用 Deployment 页的新建表单及接口，支持 API / Webhook。当前 Workflow 固定，不再要求重复选择；使用画布具体版本，有未保存修改时先保存并使用提交返回的版本。保存失败不创建部署。
- 创建后的密钥仅在成功面板内存中展示，默认遮蔽。切换执行与部署页签保留成功面板，不把密钥写入关联列表、日志或本地存储。
- 下方分页展示该 Workflow 全部版本的关联部署，含名称、类型、可复制 ID、详情链接、绑定版本及上线状态。更新未完成时另显示实际运行版本，不能把目标版本当成已经上线。
- 部署列表页支持 Workflow 筛选，关联列表跳转带上筛选参数；列表统计遵循相同 Workflow 范围。
- 每个大版本各自的最新子版本可编辑，最新版具体地址自动解析到该大版本 `/vN`；历史子版本只读。来自任务、部署等入口的显式 `snapshot=1` 只读视图继续保持只读。历史版本可用于执行、部署和另建大版本，不允许原地编辑。
